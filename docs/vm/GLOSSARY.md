# SubsetJuliaVM 用語集

この用語集は、[BLOG.md](BLOG.md)を読むための補助資料である。
対象は、Julia 本家を使ったことがあり、言語処理系やコンパイラ周りに関心のある読者である。

各項目は、Julia や一般的な言語処理系で使われる概念との対応を示しつつ、SubsetJuliaVM の実装でどう現れるかを説明する。
正確な挙動が必要なときは、各項目の Rust ソースと [BLOG.md](BLOG.md)を参照する。

## 全体の地図

Julia のプログラムは、次の順に形を変える。

```text
ソースコード
    ↓ 字句解析と構文解析
CST
    ↓ lowering
Core IR の Program
    ↓ 型推論とバイトコードコンパイル
CompiledProgram
    ↓ VM
実行時の Value
```

**ソースコード**は人間が書く文字列である。
**CST**は文字列の文法構造を表す木である。
**Core IR**は、文法の違いを整理して意味を扱いやすくした中間表現である。
**CompiledProgram**は VM が実行する命令列とメタデータの集合である。
**Value**は VM が計算中に保持する実際の値である。

AoT はこの流れの Core IR から分岐する。
AoT では VM 用バイトコードではなく、生成 Rust または Cranelift 用の別表現を作る。

### 静的パイプライン

**静的パイプライン**は、プログラムの実行前にソースコードを解析し、最終的な実行形式（VM 用バイトコード）を生成しておき、実行時はそれを解釈する方式である。

SubsetJuliaVM では、Parser → Lowering → Compiler → VM バイトコードの各段階が実行前に完了する。
実行時に LLVM codegen や CPU の機械語生成を行わないため、iOS や WebAssembly のような制限された環境で動かせる。

## 文字列から構文木へ

### 字句解析

**字句解析**は、文字列を意味のある最小単位へ分ける処理である。

SubsetJuliaVM の **lexer** は、識別子、数値、演算子、括弧などを **token** として作る。
lexer は文全体の意味を決めず、後段が読める単位を出力する。

### token

**token**は、字句解析で得られる一つの記号である。

`x = 1 + 2` なら、`x`、`=`、`1`、`+`、`2` が token になる。
token は通常、種類と元ソース中の位置を持つ。

### パーサー

**パーサー**は、token の並びが文法に合うかを調べ、構造を組み立てるプログラムである。

SubsetJuliaVM の標準パーサーは Rust で書かれた再帰下降パーサーである。
パーサーは lexer の token を順に読み、関数定義、条件分岐、型注釈などの構造を認識する。

### CST

**CST（Concrete Syntax Tree）**は、ソースコードの文法上の形を保持する木構造である。
木の頂点が構文要素を表し、親子関係が入れ子構造を表す。

SubsetJuliaVM の `CstNode` は、構文種別、子ノード、フィールド名、ソース位置を持つ。
同じ意味になる書き方でも、括弧や構文糖の違いが CST に残ることがある。

### AST

**AST（Abstract Syntax Tree）**は、表記上の細部を省いて意味に近づけた構文木である。
CST が括弧やキーワードの配置を詳しく保存するのに対し、AST はコンパイラが必要とする構造に絞る。

SubsetJuliaVM の主経路には独立した AST 構築段階がなく、CST から Core IR へ直接 lowering する。
CLI の `--dump-ast` という名前は歴史的であり、表示される木は CST である。

### Span

**Span**は、ソースコード中の位置範囲である。

SubsetJuliaVM の `Span` は、byte offset、行番号、列番号などを使って構文要素やエラーの位置を表す。
Rust の型は [subset_julia_vm_ir/src/span.rs](../../subset_julia_vm_ir/src/span.rs)にある。

### 構文エラー

**構文エラー**は、token の並びが文法に合わないときに発生するエラーである。

パーサー内部の `ParseError` は多くの種別で `Span` を持つ。
パイプラインが公開する `SyntaxError::ParseFailed` は文字列だけの場合があるため、すべての構文エラーが同じ粒度の位置情報を持つわけではない。

## 構文木から意味表現へ

### lowering

**lowering**は、表層構文を、後続処理が扱いやすい意味的な表現へ変換する処理である。

SubsetJuliaVM は CST を直接 Core IR の `Program` へ変換する。
関数、型、モジュール、マクロなどは Program の定義領域へ入り、実行文は `main` へ入る。

### Core IR

**Core IR（Core Intermediate Representation）**は、構文の細部を整理した中間表現である。
IR は「中間表現」を意味し、入力ソースと最終的な実行命令の間に置かれる。

SubsetJuliaVM の Core IR は、関数、型定義、モジュール、`using`、マクロ、`main` を一つの `Program` にまとめる。
正準な定義は [subset_julia_vm_types/src/ir/core.rs](../../subset_julia_vm_types/src/ir/core.rs)にある。

### Program

**Program**は、lowering 後の一つの Julia プログラム全体を表す構造体である。

Program はまだ VM の命令列ではない。
コンパイラは Program を調べ、関数情報、型情報、メソッド表、バイトコードを作る。

### マクロ

**マクロ**は、プログラムを実行する前に別のプログラム断片へ展開する仕組みである。
Julia のマクロは構文木を扱う。

SubsetJuliaVM のマクロ VM が返す `Value::Expr` は、CST へ戻さず Core IR の `Stmt` または `Expr` へ変換される。
マクロの展開結果も通常のコンパイル経路に入る。

### スコープ

**スコープ**は、名前と値の対応が有効な範囲である。

**hard scope** では、関数や `let` などのローカル束縛が明確に決まる。
**soft scope** では、トップレベルの loop にある代入が既存のグローバルを更新するか、新しいローカルを作るかを実行モードが決める。

### strict mode と lenient mode

**strict mode**は、ファイル実行に近い soft scope の扱いである。
曖昧な代入を新しいローカルとして扱うため、読み出しが先にあると未定義変数エラーになることがある。

**lenient mode**は、対話実行に近い扱いである。
既存のグローバルがあれば、そのグローバルを更新する解釈を許す。

## 型と推論

### JuliaType

**JuliaType**は、Julia の言語上の型を表す型表現である。
宣言に書かれた型や、実行時の型名を扱うときに使う。

`Int64` や `Vector{Float64}` のような型の意味を、言語に近い形で表す。

### CoreType

**CoreType**は、部分型判定とメソッド選択に適した正準型表現である。

`UnionAll`、型変数、タプル型、可変長引数など、ディスパッチに必要な構造を保持する。
メソッド表の正準シグネチャにも利用する。

### LatticeType

**LatticeType**は、型推論が持つ「現在分かっていること」を表す抽象的な値である。
抽象解釈の結果を、情報量の順序を持つ型の束（lattice）として表す。

`Bottom` は到達しない状態、定数型は値まで分かった状態、`Top` はほとんど何も分からない状態を表す。
推論は式を読みながら LatticeType を更新し、情報が変化しなくなるまで繰り返す。

### 型の束

**型の束**は、型情報を「どちらがより詳しいか」という順序で並べた構造である。

SubsetJuliaVM の型の束では、`Top` から具体型や定数型へ情報が増える方向に推論が進む。
異なる経路から来た情報を安全にまとめるため、型の共通の上限や下限を計算する。

### 抽象解釈

**抽象解釈**は、実際の値を一つずつ計算せず、値の性質を抽象値で計算する方法である。

SubsetJuliaVM の推論エンジンは、関数の引数や式の結果に LatticeType を割り当てる。
この情報が、戻り値の型、直接呼び出せるメソッド、型付き命令の選択に使われる。

### 固定点

**固定点**は、ある計算をもう一度適用しても結果が変わらない状態である。

推論では、関数呼び出しを通じて型情報が循環することがある。
推論エンジンは情報を繰り返し伝播し、結果が安定した固定点に達したときに解析を終える。

### SSA

**SSA（Static Single Assignment）**は、各変数の値を一つの定義箇所から生じたものとして扱う中間表現である。

SSA にすると、ある計算結果をどの式が作ったかを追いやすくなる。
SubsetJuliaVM は対象条件を満たす非自明なユーザー関数で SSA 経路を試し、対応できない関数は別のコンパイラ経路へ戻す。

### 型安定性

**型安定性**は、ある関数へ同じ型の入力を与えたとき、内部の値の型と戻り値の型が予測しやすい性質である。

型安定性が高いと、VM は一般的な値操作より狭い型の命令を選びやすい。
型安定性は Julia の型システムそのものではなく、プログラムの性質を表す。

## メソッド選択とディスパッチ

### メソッド

**メソッド**は、関数名と引数型の条件に結び付いた一つの関数定義である。
同じ関数名でも引数型の条件が違えば、別のメソッドとして登録できる。

たとえば `f(x::Int64)` と `f(x::Float64)` は、名前は同じでも異なるメソッドである。

### シグネチャ

**シグネチャ**は、メソッドを識別するための名前、引数型、可変長引数の形状などの組である。

コンパイラ側では `CoreType` を使った正準シグネチャを持ち、prelude とユーザー定義を結合するときには lowering 段階のシグネチャ文字列も使う。

### 複数ディスパッチ

**複数ディスパッチ**は、すべての引数の型を使って呼び出すメソッドを選ぶ仕組みである。

SubsetJuliaVM はコンパイル時に型が分かる呼び出しを直接選択し、型が分からない呼び出しを VM の実行時ディスパッチへ送る。

### ディスパッチ

**ディスパッチ**は、呼び出し時にどのメソッドを実行するかを決める操作である。
ディスパッチは関数を実行することではなく、実行すべき関数を選ぶ段階である。

### specificity

**specificity**は、複数の候補のうち、どの引数条件がより具体的かを比較する尺度である。

`Int64` に特化したメソッドと、すべての `Number` を受け取るメソッドがあれば、通常は前者の条件が具体的である。

### ambiguity

**ambiguity**は、同じ呼び出しに同程度に適用できる候補が複数あり、一つを安全に選べない状態である。

SubsetJuliaVM は specificity だけで一意に決まらない場合を曖昧性として扱い、任意に候補を選ばない。

### caller と callee

**caller**は、別の関数を呼び出す側の関数である。
**callee**は、呼び出される側の関数である。

`f(x) = g(x) + 1` では、`f` が caller、`g` が callee になる。
SubsetJuliaVM では、caller が知っている型情報が callee へ自動的に渡るわけではないため、callee は実際に渡された値の型を見てメソッド選択や特殊化を行う。

### 静的ディスパッチと動的ディスパッチ

**静的ディスパッチ**は、実行前に引数型が分かるため、コンパイラが呼び出し先を決める方式である。
**動的ディスパッチ**は、実行時の `Value` と VM の型情報を使って呼び出し先を決める方式である。

静的ディスパッチは速い命令を出しやすいが、未知の値には使えない。
動的ディスパッチは未知の値を扱えるが、候補探索と型比較のコストが発生する。

### 境界

**境界**は、ふたつの処理や領域が接するところであり、そこをまたぐと文脈や情報が変わる点である。

たとえば、関数呼び出しの境界では、呼び出し側（caller）から呼ばれる側（callee）へ値は渡るが、caller が知っている型情報が callee には自動的には渡らない。
SubsetJuliaVM ではこの境界を越えて型情報を伝搬させないため、`f(x)` から呼ばれた `g(x)` は `f` の仮引数型を知らず、実際に渡された値の型を見て処理を選ぶ。

他にも FFI 境界や REPL とホストの境界など、異なる言語や実行環境が接するところでも使われる。

## 実行する命令と値

### バイトコード

**バイトコード**は、仮想機械が読むための中間的な命令列である。
CPU の機械語ほどハードウェアに依存せず、ソースコードほど人間向けでもない。

SubsetJuliaVM の標準経路が生成するバイトコードは、`Instr` の列として `CompiledProgram` に保存される。

### Instr

**Instr**は、SubsetJuliaVM のバイトコードを構成する一つの命令である。

`LoadAddConstI64Slot` や `DivF64` のように、入力の型に合わせた命令もある。
`CallDynamic` や `CallTypedDispatch` は、実行時のメソッド選択を依頼する命令である。

### CompiledProgram

**CompiledProgram**は、コンパイラの最終生成物で、VM が実行するバイトコード列とメタデータをまとめた構造体である。

関数ごとの `Instr` 列に加えて、関数表、メソッド表、型情報、スロット割り当て、ソースマップを持つ。
`Vm::new_program` は CompiledProgram を受け取って実行を開始する。

### wire name

**wire name**は、命令や組み込み処理を直列化やキャッシュで識別するための安定した内部名である。

人間向けの表示名とは独立に保たれ、バイトコードキャッシュの互換性の基準になる。
たとえば動的 `+` の内部タグは、wire name `add_float` に由来する `AddFloat` と表示されていたが、浮動小数点専用と誤解されやすいため、現在の `--dump-bytecode` では `DynamicAdd` と表示される。

### スタック VM

**スタック VM**は、値を積むスタック（**値スタック**）と、命令位置を使って命令を実行する仮想機械である。

命令はスタックから値を取り出し、計算結果をスタックへ戻す。
SubsetJuliaVM の標準実行系はスタック VM であり、レジスタ VM は opt-in の実験経路である。

### レジスタ VM

**レジスタ VM**は、値を番号付きの場所（レジスタ）に置き、命令がその番号を直接指定する仮想機械である。

SubsetJuliaVM では既定の実行系ではなく、明示的に選ばれた対象関数だけを処理する。
対応できない関数はスタック VM へ戻る。

### Value

**Value**は、VM が実行時に扱う値の列挙型である。
整数、浮動小数点数、真偽値、文字列、タプル、構造体参照などを一つの型で表す。

Value は Julia の型体系そのものではない。
型を判定するには、Value に加えて VM の struct heap や型定義を調べる場合がある。

### ValueType

**ValueType**は、VM の命令選択や実行時特殊化に使う粗い型タグである。
精密な型式をすべて保存するのではなく、整数か浮動小数点数か配列か、といった高速な判断に必要な情報を残す。

ValueType は Julia の完全な型と同じではない。
たとえば型パラメータや配列の次元数を省略する場合がある。

### boxed な値

**boxed**は、具体的な型の値を、どの型でも入る共通の入れ物に包んで扱うことである。

SubsetJuliaVM の汎用経路は、整数も浮動小数点数も `Value` に包んで値スタックで受け渡す。
型付きスロットや型付き命令が使える場所では、boxed な `Value` を作らず `i64` や `f64` のまま計算できるため速い。

### フレーム

**フレーム**は、一つの関数呼び出しに必要なローカル変数、引数、戻り先などを保持する領域である。

VM は関数を呼び出すたびにフレームを作り、関数が戻るとそのフレームを片付ける。

### スロット

**スロット**は、フレーム内の値を置く番号付きの場所である。
変数名を毎回文字列で検索する代わりに、コンパイラが変数を番号へ割り当てる。

型が分かるスロットには、整数用や浮動小数点数用のアクセサを使える。
型が分からない場合は一般的な `Value` 用の経路へ戻る。

### ソースマップ

**ソースマップ**は、バイトコードの命令位置と元ソースコードの `Span` を対応付ける表である。

実行時エラーが命令位置を持っていれば、ソースマップを通じて元の Julia コードの位置を表示できる。

## コンパイルの最適化

### コンパイラ

**コンパイラ**は、ある表現を別の実行しやすい表現へ変換するプログラムである。

SubsetJuliaVM のコンパイラは Core IR を調べ、関数情報、メソッド候補、型情報、バイトコードを作る。

### スロット化

**スロット化**は、変数名をフレーム内の番号付きスロットへ割り当てる処理である。

スロット化後は、命令が文字列名を探さずに番号から値を読めるため、実行時の検索を減らせる。

### peephole 最適化

**peephole 最適化**は、命令列の短い範囲を見て、同じ結果をより少ない命令へ置き換える処理である。

SubsetJuliaVM では、定数演算の融合や不要な命令の削除などを行う。
最適化の前後で意味が変わらないことが条件になる。

### superinstruction（融合命令）

**superinstruction**（**融合命令**）は、頻繁に連続する複数命令を一つの命令として扱う仕組みである。
命令のたびに共通の準備処理を繰り返すコストを減らすために使う。

`LoadAddConstI64Slot` は「スロットを読む」「定数を足す」を 1 命令にまとめた融合命令である。
superinstruction は CPU の機械語ではない。
VM が読むバイトコードの命令種類を増やして、インタープリターの処理を短くする。

### インライン展開

**インライン展開**は、関数呼び出しを、呼び出し先の本体を埋め込んだ命令列へ置き換える最適化である。

SubsetJuliaVM では、呼び出し地点で引数の型が分かる場合に、小さな関数の本体を main バイトコードへ直接展開し、型付き命令や融合命令へ畳むことがある。
バイトコード dump に現れる `__sjulia_inline_arg_f_0` のようなスロットは、この展開が作った引数受け渡し用のスロットである。

### SROA

**SROA（Scalar Replacement of Aggregates）**は、struct のような集約値をフィールドごとの独立したスカラー値へ分解する最適化である。

SubsetJuliaVM では複素数が代表的な対象で、`ComplexF64` の実部と虚部を別々の `Float64` スロットとして扱えれば、struct の構築と参照を減らせる。
性能の議論で「specialized body の SROA 形状」と言うときは、実行時特殊化が生成した本体でこの分解がどこまで効いているかを指す。

### キャッシュ

**キャッシュ**は、以前に計算した結果を保存し、同じ条件で再利用する仕組みである。

SubsetJuliaVM は、prelude の Core IR、Base のバイトコード、完全な `CompiledProgram`、実行時のメソッド選択などを別々のキャッシュとして扱う。
キャッシュには型やコンパイラの fingerprint を付け、古い結果を誤って使わないようにする。

### prelude と Base

**prelude**は、ユーザーコードの前に読み込む初期 Julia 定義の集合である。
**Base**は、基本的な型、演算、関数、標準機能を提供する同梱 Julia コードと Rust の組み込み処理である。

prelude は lowering 済みの Program としてユーザー Program へ結合される。
Base のバイトコードキャッシュは、ユーザーコードのコンパイルを速くするために使われる。

release バイナリのビルド時に `SJULIA_PRELUDE_PROGRAM_CACHE` と `SJULIA_BASE_CACHE` を指定すると、これらのキャッシュをバイナリ自体へ埋め込める。
埋め込み済みバイナリは起動時に Base をソースから再コンパイルしないため、cold start が速い。
BLOG の benchmark や iOS・Raspberry Pi 向けの配布バイナリはこの形を使う。

## 実行時の特殊化と別バックエンド

### 実行時バイトコード特殊化

**実行時バイトコード特殊化**は、実行中に具体的な引数型へ合わせたバイトコードを追加生成する処理である。
これは CPU の機械語を生成する JIT ではなく、同じ VM が読める `Instr` を増やす処理である。

`CallSpecialize` は、型注釈のない引数を持つ関数などを対象にし、具体的な `ValueType` の組が現れたときに特殊化を試す。
特殊化できない場合は汎用バイトコードへ戻る。
特殊化に成功した本体は `specialization_i64_cache` などのキャッシュに保存され、以降の呼び出しで再利用される。

### 型付きループ

**型付きループ**（typed loop）は、ループ内の値型が安定していると分かったとき、ループ本体を型付き命令の実行ブロックとして動かす仕組みである。

ループ内で型注釈のない関数が `Int64` や `Float64` の引数で呼ばれる場合は、`CallSpecializeI64Slots` のような融合命令を通じて、実行時特殊化が生成した本体を型付きブロックから呼ぶ。
メソッドの再定義などで特殊化キャッシュが無効化されると、汎用実行へ自動的に戻る。

### JIT

**JIT（Just-In-Time compilation）**は、プログラムの実行中に CPU の機械語などを生成するコンパイル方式である。
通常のコンパイラが実行前に変換を終えるのに対し、JIT は実行時に得た情報を利用できる。

SubsetJuliaVM の標準 VM にある `CallSpecialize` は JIT ではない。
これは VM バイトコードを追加する実行時特殊化であり、Cranelift を使う AoT の別経路とも区別する。

### AoT

**AoT（Ahead-of-Time compilation）**は、プログラムを実行する前に、実行用のコードや成果物を生成する方式である。

SubsetJuliaVM の AoT は Core IR から分岐し、不要コード除去、AoT 用推論、`AotProgram`、最適化を通って Rust または Cranelift の出力を作る。
標準の `sjulia`、C ABI、Web API のソース実行が暗黙に AoT へ切り替わるわけではない。

### Cranelift

**Cranelift**は、Rust などから機械語やオブジェクトファイルを生成するためのコード生成ライブラリである。

SubsetJuliaVM では `cranelift` feature を有効にしたときだけ利用できる。
Cranelift 経路は実験的であり、標準 VM の実行経路ではない。

### dead-code elimination

**dead-code elimination**（不要コード除去）は、実行結果に影響しない定義や命令を取り除く最適化である。

AoT の前段では、入口から到達できない関数や命令を除去して、生成対象を小さくする。
除去できると判断するには、到達性を安全に証明できなければならない。

### AoT ランタイム

**AoT ランタイム**は、AoT が生成した Rust コードを実行するための補助ライブラリである。
標準 VM の内部とは別の `Value`、エラー、演算、乱数などを提供する。

現在の AoT ランタイムには、動的メソッド選択が未完成な経路や、`throw` を panic へ変換する経路がある。
そのため、AoT の対応範囲を標準 VM と同じだと仮定してはいけない。

### juliars

**juliars**は、SubsetJuliaVM の AoT バックエンドを起動するコマンドラインツールである。

Julia ソースから Rust コードを生成し、ネイティブの実行バイナリを出力する（`--emit-binary`）。
benchmark 表の `juliars` 行は、この生成バイナリの実行時間である。
対応範囲は標準 VM より狭く、`--minimal-prelude` の指定が必要になる場合がある。

## 実行状態とメモリ

### ヒープ

**ヒープ**は、関数のローカル変数やスタックとは別に、実行中の値を保持するメモリ領域である。

SubsetJuliaVM の `struct_heap` は、可変 struct の実体を保存する VM 所有の領域である。
`Value::StructRef` はその領域の添字を保持する。

### StructRef

**StructRef**は、可変 struct の実体を直接コピーせず、VM の struct heap の添字で参照する値である。

参照先を移動すると添字の更新が必要になる。
そのため VM は、ヒープを圧縮するときにスタック、フレーム、入れ子の値の参照をまとめて更新する。

### Rc と RefCell

**Rc**は、一つのデータを複数の所有者から共有するための参照カウント付きポインターである。
**RefCell**は、Rust の通常の借用規則を実行時に検査しながら、内部の値を変更するための容器である。

SubsetJuliaVM は、文字列や可変コレクションなどの共有 payload に `Rc` と `RefCell` を使う。
すべての値がこの方式ではなく、整数の inline 表現、タプルの `Vec`、範囲のフィールドなども使い分ける。

### mark/compact

**mark/compact**は、使われているオブジェクトを印付けし、不要なオブジェクトを除いて残りを詰めるメモリ管理方式である。

SubsetJuliaVM では、VM のルートから到達できる `StructRef` を mark し、`struct_heap` の生存要素を連続した添字へ移す。
これは VM 全体のメモリを一律に管理する GC ではなく、struct heap に限定した処理である。

### single-threaded

**single-threaded**は、一つの VM や REPL セッションを一つのスレッドだけが所有する設計である。

SubsetJuliaVM は `Rc`、`RefCell`、thread-local state を使うため、VM と REPL の同時利用を複数スレッドへ自動的に広げない。
REPL には所有スレッドを検査する debug guard がある。

### StableRng

**StableRng**は、seed から決定的に乱数列を生成する SubsetJuliaVM 同梱の乱数生成器である。

プラットフォームや実行回によらず同じ列を再現できるため、fixture テストの結果比較に使われる。
`Vm::new_program(compiled, StableRng::new(seed))` のように VM 生成時に渡す。

## REPL とホスト境界

### REPL

**REPL**（Read-Eval-Print Loop）は、入力を読み、評価し、結果を表示する対話環境である。
一度のプログラム実行で終わらず、前の入力で定義した名前や値を次の入力へ引き継ぐ。

SubsetJuliaVM の `REPLSession` は、グローバル値、関数メソッド、型、モジュール、マクロ、直前の値を保存する。

### live delta

**live delta**は、保持中の VM に新しい定義や命令を差分として追加し、その VM へ再入する方式である。

既存の VM 状態を保てる入力だけが対象になる。
モジュールや再定義などで状態の再構築が必要になると、別の経路へ戻る。

### fresh delta

**fresh delta**は、過去にコンパイルした先頭部を再利用し、新しい入力だけをコンパイルして、新しい VM を作る方式である。

live delta より再構築の範囲が広いが、蓄積した全ソースコードを毎回最初からコンパイルする必要はない。

### full compile

**full compile**は、蓄積した定義全体をもう一度結合し、lowering とコンパイルをやり直す経路である。

差分だけでは意味を保てない入力や、以前のキャッシュが使えない入力で選ばれる。

### FFI

**FFI（Foreign Function Interface）**は、異なる言語や実行環境の間で関数を呼ぶための境界である。

SubsetJuliaVM の FFI クレートは C ABI の関数を公開し、iOS や native host から Rust VM を呼べるようにする。
主要な入口は panic を C 境界へそのまま伝えない処理で囲む。

### C ABI

**C ABI**は、C 言語から関数、引数、戻り値、構造体をどう見せるかを定める規約である。
関数名の符号化、整数の幅、メモリの所有権、エラーの返し方が一致しなければ、別言語から安全に呼べない。

SubsetJuliaVM は C ABI の互換性番号を Cargo クレートの version とは別に管理する。

### wasm-bindgen

**wasm-bindgen**は、WebAssembly の Rust 関数を JavaScript から呼び出しやすくするための境界生成ツールである。
WebAssembly は CPU の命令を直接配布するのではなく、ブラウザーなどの実行環境で動く形式である。

SubsetJuliaVM の Web クレートは、Rust パーサーと標準 VM を `wasm-bindgen` 経由で公開する。

## 実行環境と性能を読む語

### CPU

**CPU**は、コンピュータの命令を実行する中心的な部品である。

Julia 本体の JIT は、実行中に CPU が直接読める機械語を生成する。
SubsetJuliaVM の標準 VM は CPU の機械語を新しく生成せず、Rust で書かれた VM がバイトコードを読む。

### LLVM

**LLVM**は、コンパイラが機械語を作るときに使う基盤である。
多くの言語処理系が、独自の中間表現を LLVM に渡し、各 CPU 向けの機械語生成を任せる。

Julia 本体は LLVM を使って高速なネイティブコードを生成する。
SubsetJuliaVM の標準 VM 経路は LLVM を使わず、独自バイトコードを VM で実行する。

### WebAssembly

**WebAssembly**は、ブラウザなどで実行できる低水準のバイナリ形式である。
JavaScript だけでは重い計算を、Rust や C などから生成したコードとして配布できる。

SubsetJuliaVM の Web クレートは、Rust の VM を WebAssembly として公開する。
これにより、ブラウザ上でも小さな Julia 風コードを実行できる。

### static library

**static library**は、アプリをビルドするときに実行ファイルへ組み込まれるライブラリである。
実行時に別ファイルとして探すのではなく、ビルド時に結合される。

SubsetJuliaVM の FFI クレートは iOS 向けに static library を作れる。
Swift 側のアプリは C ABI を通して Rust VM を呼び出す。

### native library

**native library**は、特定の OS と CPU 向けにコンパイルされたライブラリである。
ブラウザ上の JavaScript ではなく、端末や PC の実行環境で直接動く。

SubsetJuliaVM では、iOS や Android のアプリから Rust コアを native library として呼ぶ設計を取れる。
ホスト側の UI が異なっても、構文解析と VM 実行の中核を共有できる。

### benchmark

**benchmark**は、同じ計算を複数の実行環境で走らせ、時間やメモリ使用量を比べる測定である。
条件が変わると結果も変わるため、入力サイズ、実行方式、測定日を合わせて読む必要がある。

SubsetJuliaVM の benchmark は、Julia upstream、sjulia VM、sjulia AoT、Python などを同じ課題で比較する。
結果は「その課題とその測定条件での性能」を示すものであり、全プログラムでの順位を証明するものではない。

### cold start と warm run

**cold start**は、キャッシュが何もない状態からの初回実行である。
**warm run**は、必要なキャッシュが揃った状態での実行である。

sjulia の CLI では、cold start の時間は Base のコンパイルに支配されやすく、VM 自体の実行速度とは別の値になる。
BLOG の benchmark は、prelude/Base キャッシュを埋め込んだ release バイナリでの warm run を報告している。

### uv

**uv**は、Python の処理系とパッケージを管理する高速なコマンドラインツールである。

BLOG の benchmark では `uv run --python 3.14` の形で CPython 3.14 の実行環境を固定するために使う。
表の「Python 3.14 (uv)」はこの方法で実行した時間である。

### Cython

**Cython**は、Python 風の構文に C の型注釈（`cdef`）を加えたソースを C へ変換し、ネイティブ拡張としてコンパイルする処理系である。

BLOG の Cython 行は、型注釈に加えて複素数の実数分解のような手書き最適化を含む追試である。
同じソースを動かす処理系比較ではなく、手書き最適化の上限を示す参考値として読む。

### W^X

**W^X**（Write XOR Execute）は、同じメモリページを「書き込み可能」と「実行可能」の両方にできないポリシーである。
OS カーネルや Hardened Runtime が強制し、JIT コンパイラが実行中に機械語を生成して即座に実行するのを防ぐ。

iOS では通常のアプリが `mmap` や `mprotect` で `PROT_WRITE | PROT_EXEC` を要求できないため、LLVM を使う Julia 本家の JIT はそのまま動かせない。
SubsetJuliaVM は実行中に機械語を生成せず、静的に作った VM バイトコードを実行するのでこの制限を回避する。

### scalar loop

**scalar loop**は、配列全体の演算を一括で書くのではなく、各要素を一つずつ処理する loop である。

SubsetJuliaVM の Mandelbrot benchmark では、ComplexF64 の値を一つずつ更新する for-loop 版を scalar for-loop と呼んでいる。
型が安定している scalar loop は、VM の型付き高速経路の効果を見やすい。

### broadcast

**broadcast**は、配列の各要素へ同じ関数や演算を広げて適用する書き方である。

Julia では `f.(xs)` や `xs .+ 1` のような記法で broadcast を書く。
SubsetJuliaVM の benchmark では、ComplexF64 の格子全体へ Mandelbrot 計算を適用する形を broadcast 版として測定している。
呼び出し地点で配列の要素型が分かる場合、sjulia は要素関数へ型を伝播させた一括実行経路（bulk typed broadcast kernel）を使うことがある。

## エラーとキャッシュを追う語

### VmError

**VmError**は、VM の実行中に発生したエラーを表す型である。
ゼロ除算、型の不一致、範囲外アクセス、未対応操作などを区別する。

Julia の `try` と `catch` へ渡せるエラーと、内部エラーやキャンセルなどのホスト向けエラーは同じではない。

### source map

**source map**は、バイトコード命令の位置から元ソースコードの `Span` を引く表である。
`VmError` が最後の命令位置を持つとき、source map があればエラーを Julia の行へ戻せる。

### fingerprint

**fingerprint**は、入力や生成物の内容を短い値で識別する指紋である。
ファイルの内容が変わったかを、全内容の比較なしで確認するために使う。

SubsetJuliaVM のキャッシュはソースコード、命令表、コンパイラのビルド情報などから fingerprint を作る。
fingerprint が一致しないキャッシュは、古い命令や型情報を含む可能性があるため再利用しない。

### package loader

**package loader**は、`using` されたパッケージのソースコードやキャッシュを探し、Program に読み込む機構である。
パッケージ管理システム全体を意味せず、SubsetJuliaVM が対応する directory layout と load path を扱う。

### UnsupportedFeature

**UnsupportedFeature**は、処理系がまだ実装していない構文や操作を表すエラーである。
入力を別の意味へ黙って変換するのではなく、どの機能を扱えないかとソース位置を報告する。

## 開発時に使う道具

### --dump-bytecode

**--dump-bytecode**は、コンパイル済みバイトコードを表示する sjulia CLI のオプションである。

スロットの型、型付き命令や融合命令の選択、直接呼び出しと動的呼び出しの別を確認できる。
既定ではユーザー定義関数と main の末尾を表示し、`--all` を付けると Base や prelude の関数も含める。
BLOG のバイトコード例はこの出力から採っている。

### ラチェット

**ラチェット**（ratchet）は、望ましくない指標の現在値をベースラインとして記録し、増加を検査で拒否して減少だけを許す品質管理の仕組みである。
一方向にしか回らない工具のラチェットレンチが語源で、一度減った値が二度と増えないことを機械的に保証する。

手順は三段階からなる。
まず現在の違反箇所数をベースラインとしてリポジトリにコミットする。
次に audit スクリプトが実際の箇所数を数え、ベースラインを超えた変更を fail にする。
負債を減らす変更が入ったら、同じ変更でベースラインも下げる。

この方式なら、既存の負債をすべて直し終える前に検査を有効化でき、それ以降の悪化だけを止められる。
「新しいコードでは気をつける」という規約は忘れられるが、ラチェットは人間の記憶に依存しない。

SubsetJuliaVM では、panic 源の箇所数（`docs/vm/PANIC_FREE_RATCHET_BASELINE.tsv`）、名前文字列ベースの型 identity 参照数（`scripts/check_name_based_lookup.sh`）、julia と sjulia の既知出力差分（fixture parity sweep の allowlist TSV）などがラチェットとして運用されている。
ベースラインの更新を忘れたり、audit スクリプト自体が実行登録されていなかったりするとラチェットは機能しないため、検査の登録状況も含めて保守する必要がある。

## 用語を読む順序

最初に「ソースコードから Core IR へ」の項目を読み、次に型とメソッド選択を読むと、コンパイラが何を判断しているか分かりやすい。
その後でバイトコード VM と実行時特殊化を読むと、JIT と VM バイトコードの違いを区別できる。
最後に REPL、FFI、WASM、AoT を読むと、同じ Core IR から複数のホストとバックエンドが分岐する構造を追える。
benchmark の表を読むときは、「実行環境と性能を読む語」の cold start と warm run、uv、Cython、そして「実行時の特殊化と別バックエンド」の juliars の項を先に見ると、各行の意味が分かる。
