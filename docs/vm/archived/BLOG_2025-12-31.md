# SubsetJuliaVM: iOS で動く Julia サブセット実行環境

**ステータス**: archived; 2025-12-31 時点の技術記事スナップショットです。
アーキテクチャの詳細はその後変化している可能性があります。現在の正規概要は
[ARCHITECTURE_OVERVIEW.md](../ARCHITECTURE_OVERVIEW.md) を参照してください。

Julia のサブセットを iOS デバイス上で実行する、完全に静的なパイプライン「SubsetJuliaVM」の技術解説です。

---

## はじめに

### なぜ SubsetJuliaVM を作ったのか

Julia は数値計算に優れた言語ですが、iOS アプリで Julia コードを実行するのは困難でした。理由は：

- **JIT コンパイル**: Julia は実行時にコードを生成するため、App Store の審査に通らない
- **巨大なランタイム**: フル Julia ランタイムは iOS アプリには重すぎる
- **動的コード生成**: セキュリティポリシーに抵触する可能性

SubsetJuliaVM は、これらの制約を回避しつつ、Julia の**サブセット**を iOS で安全に実行できるようにしました。

### iOS で JIT が禁止されている根拠

iOS で JIT コンパイルや動的コード生成が禁止されている理由と根拠を整理します。

#### 1. App Store Review Guidelines 2.5.2

[App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) の **2.5.2** に明記されています：

> Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they **download, install, or execute code which introduces or changes features or functionality of the app**, including other apps.

**要約**: アプリは自己完結型でなければならず、アプリの機能を変更するコードをダウンロード・インストール・**実行してはならない**。

#### 2. 技術的制約: W^X (Write XOR Execute)

iOS カーネルレベルで **W^X ポリシー** が強制されています：

| メモリ領域 | 書き込み | 実行 | 説明 |
|-----------|---------|-----|------|
| コード領域 | ✗ | ✓ | 実行専用 |
| データ領域 | ✓ | ✗ | 書き込み専用 |
| JIT に必要 | ✓ | ✓ | **iOS では不可** |

JIT コンパイラは「メモリに書き込んだコードを実行する」必要がありますが、iOS ではこの組み合わせが禁止されています。これはセキュリティ上の理由で、マルウェアが実行時にコードを生成・実行することを防ぐためです。

#### 3. 例外: 特定のエンタイトルメント

[com.apple.security.cs.allow-jit](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.cs.allow-jit) というエンタイトルメントが存在しますが、制限があります：

- **macOS 専用**（iOS では使用不可）
- App Store 配布アプリでは使用できない
- 主にデバッガや開発ツール用

#### 4. EU DMA 対応: BrowserEngineKit (2024年〜)

EU の Digital Markets Act 対応として、Apple は [BrowserEngineKit](https://developer.apple.com/documentation/browserenginekit) を導入しました。これにより JIT が可能になりますが：

- **EU 地域のみ**で利用可能
- **ブラウザエンジン専用**（一般アプリは不可）
- 厳格な審査プロセスが必要
- [参考: Daring Fireball の解説](https://daringfireball.net/2024/06/apple_disables_webkits_jit_in_lockdown_mode)

#### 5. なぜ Apple は JIT を禁止するのか

```
JIT / 動的コード生成の危険性:
┌─────────────────────────────────────────────────┐
│  • マルウェアが実行時にコードを生成・実行できる   │
│  • 事前のコードレビューをバイパスできる          │
│  • サンドボックスの保護を弱める可能性            │
└─────────────────────────────────────────────────┘

Apple の方針:
┌─────────────────────────────────────────────────┐
│  AOT (Ahead-of-Time) コンパイルを推奨            │
│  → 実行前にすべてのコードが検証可能              │
│  → App Store 審査でコードの安全性を確認          │
└─────────────────────────────────────────────────┘
```

#### 6. SubsetJuliaVM への影響

```
JIT が使えない
    ↓
実行時にネイティブコードを生成できない
    ↓
AOT (Ahead-of-Time) コンパイル + インタプリタ が必須
    ↓
SubsetJuliaVM の設計:
  Parser → Lowering → Bytecode → VM (インタプリタ)
```

**これが SubsetJuliaVM を「完全に静的なパイプライン」として設計した根本的な理由です。**

### なぜ「AOT + インタプリタ」なのか

#### コード実行の3つの方法

プログラムを実行する方法は大きく3つあります：

| 方式 | 説明 | 例 |
|-----|------|-----|
| 純粋インタプリタ | ソースを直接解釈実行 | 初期の BASIC, シェル |
| AOT コンパイル | 事前にネイティブコードに変換 | C, Rust, Go |
| JIT コンパイル | 実行時にネイティブコードに変換 | Julia, Java, V8 |

#### 各方式の特性

| 方式 | 実行速度 | 起動速度 | 動的コード実行 | iOS対応 |
|-----|---------|---------|--------------|---------|
| 純粋インタプリタ | 遅い | 速い | ✓ | ✓ |
| AOT コンパイル | 速い | 速い | ✗ | ✓ |
| JIT コンパイル | 速い | 遅い | ✓ | **✗** |

#### ユーザー入力を実行したい場合の選択肢

SubsetJuliaVM の目的は「ユーザーが入力した Julia コードを実行する」ことです。

**選択肢1: 純粋 AOT（不可能）**

```
ユーザー入力 → ネイティブコードにコンパイル → 実行
                        ↑
                  iOS で禁止（実行時のコード生成）
```

**選択肢2: 事前コンパイル済みのみ（制限的）**

```
開発時: Julia コード → アプリに埋め込み
実行時: 埋め込まれたコードのみ実行可能
```

問題: ユーザーが新しいコードを入力できない。REPL が不可能。

**選択肢3: AOT + インタプリタ（SubsetJuliaVM の選択）**

```
開発時 (AOT):
  VM 自体を Rust → ネイティブコード にコンパイル
  （このコードは固定で、実行時に変更されない）

実行時 (インタプリタ):
  ユーザー入力 → バイトコード → VM が解釈実行
  （新しいネイティブコードは生成しない）
```

#### 図解: JIT vs AOT+インタプリタ

```
【JIT (iOS で禁止)】

  ユーザー入力        JIT コンパイラ      新しいネイティブコード
  "1 + 2"      →    [実行時変換]    →   [機械語]  →  実行
                                              ↑
                                    メモリに書き込んで実行（禁止）


【AOT + インタプリタ (SubsetJuliaVM)】

  ユーザー入力        バイトコード生成         VM (事前コンパイル済み)
  "1 + 2"      →    [PushI64(1),     →    [解釈実行]  →  結果: 3
                     PushI64(2),
                     AddI64]
                          ↑                      ↑
                    データとして処理      Rust で事前にコンパイル
```

#### バイトコードは「コード」ではないのか？

重要な区別があります：

| | ネイティブコード | バイトコード |
|---|---|---|
| 実行方法 | CPU が直接実行 | VM が解釈実行 |
| iOS の扱い | 「コード」= 審査対象 | 「データ」= OK |
| 実行時生成 | **禁止** | 許可 |

```
バイトコード = VM への「指示書」（データ）
ネイティブコード = CPU が直接実行する「機械語」（コード）

iOS が禁止: 「ネイティブコードの実行時生成」
iOS が許可: 「バイトコード（データ）の生成」
```

#### なぜこれが App Store で許可されるのか

```
SubsetJuliaVM の実行時の動作:

  1. ユーザーが Julia コードを入力
  2. Parser が文字列を CST に変換      ← データ構造の操作
  3. Lowering が CST を Core IR に変換  ← データ構造の操作
  4. Compiler が バイトコードに変換    ← データ構造の操作
  5. VM がバイトコードを解釈実行       ← 事前コンパイル済みコード

  → 新しいネイティブコードは一切生成されない
  → すべて「データ」として処理される
  → VM 自体は App Store 審査時に検証済み
```

#### まとめ

```
iOS の制約:
  「実行時にネイティブコードを生成・実行してはならない」

SubsetJuliaVM の解決策:
  1. VM 自体は事前に (AOT) ネイティブコードにコンパイル
  2. ユーザー入力はバイトコード（データ）に変換
  3. 事前コンパイル済みの VM がバイトコードを解釈実行

  → 実行時に新しいネイティブコードは生成されない
  → App Store の制約をクリア
  → ユーザーは自由に Julia コードを入力・実行できる
```

### VM が App Store で許可される根拠

#### Apple Developer Program License Agreement 3.3.2

[Apple Developer Program License Agreement](https://developer.apple.com/programs/information/Apple_Developer_Program_Information_8_12_15.pdf) のセクション **3.3.2** に明記されています：

> "Interpreted code may only be used in an Application if **all scripts, code and interpreters are packaged in the Application** and not downloaded."

**要約**: インタプリタ（VM）とコードが**アプリにバンドル**されていれば許可される。

#### 重要な区別: executable code vs interpreted code

| 種類 | 定義 | iOS での扱い |
|-----|------|-------------|
| Executable code | CPU が直接実行できるバイナリ | ダウンロード・生成 **禁止** |
| Interpreted code | インタプリタが処理して実行 | 条件付きで **許可** |

[The Register](https://www.theregister.com/2017/06/07/apple_relaxes_developer_rules/) より：

> "Executable code refers to code that can be run directly – compiled binary files – and interpreted code refers to code that must be processed by an interpreter to generate an executable form."

#### 許可される条件（2017年6月更新）

[Apple Developer Forums](https://developer.apple.com/forums/thread/52161) で確認された更新内容：

> "Interpreted code may be downloaded to an Application but only so long as such code:
> (a) does not change the primary purpose of the Application
> (b) does not create a store or storefront for other code
> (c) does not bypass signing, sandbox, or other security features of the OS"

#### 実際に許可されている VM ベースのアプリ

| アプリ | VM/インタプリタ | App Store |
|-------|---------------|-----------|
| [Pythonista 3](https://apps.apple.com/us/app/pythonista-3/id1085978097) | Python 3.10 | ✓ 許可 |
| Codea | Lua | ✓ 許可 |
| iSH | x86 エミュレータ | ✓ 許可 |
| a-Shell | シェル | ✓ 許可 |

これらのアプリは「VM/インタプリタがアプリにバンドル」されているため許可されています。

#### SubsetJuliaVM が許可される理由

```
SubsetJuliaVM の構成:

  ✓ VM (インタプリタ) がアプリにバンドル
    → Rust でコンパイル → 静的ライブラリ (.a)
    → XCFramework としてアプリに埋め込み

  ✓ ユーザー入力は「interpreted code」として処理
    → バイトコードに変換（データ）
    → VM が解釈実行

  ✓ 新しい executable code は生成しない
    → JIT コンパイルなし
    → ネイティブコード生成なし

  ✓ アプリの主目的を変更しない
    → Julia コードの実行が主目的として申告
```

#### 許可条件のチェックリスト

| 条件 | SubsetJuliaVM |
|-----|----------|
| インタプリタがバンドルされている | ✓ XCFramework として埋め込み |
| executable code をダウンロードしない | ✓ バイトコード（データ）のみ |
| executable code を生成しない | ✓ JIT なし |
| アプリの主目的を変更しない | ✓ Julia 実行が主目的 |
| セキュリティ機能をバイパスしない | ✓ サンドボックス内で動作 |

#### Pythonista との比較

```
Pythonista (App Store で許可):
  Python インタプリタ → アプリにバンドル
  ユーザーの Python コード → インタプリタが実行

SubsetJuliaVM (同じ構造):
  Julia サブセット VM → アプリにバンドル
  ユーザーの Julia コード → VM が実行

→ 同じカテゴリとして App Store で許可される
```

### 設計の核心

```
Julia の全構文を受理 → Lowering で判定 → Compiler で Bytecode 化 → VM が実行
```

この設計により：
- **パーサは失敗しない**（構文的に Julia なら通す）
- **サポート判定は Lowering で行う**（明確なエラーメッセージ）
- **VM は Bytecode だけ知ればよい**（シンプルで拡張可能）

## 用語の整理: 実行環境 vs 仮想マシン

SubsetJuliaVM という名前には「VM（仮想マシン）」が含まれていますが、技術的には**実行環境**です。この違いを整理します。

### 仮想マシン (VM) = エンジン

**仮想マシン**は、バイトコードを解釈・実行するインタプリタです。
CPU の「代わり」に中間命令を実行する**ソフトウェア実行エンジン**と考えると分かりやすいです。

```
入力: バイトコード命令列
      ↓
┌─────────────────────┐
│  仮想マシン (VM)     │
│  • 命令ポインタ      │
│  • スタック操作      │
│  • 演算実行          │
└─────────────────────┘
      ↓
出力: 実行結果
```

SubsetJuliaVM では `vm.rs` がこれに相当します。`PushI64(42)` → `AddI64` → `ReturnI64` のような命令を順に実行します。

### 実行環境 = 車全体

**実行環境**は、プログラムを実行するために必要なシステム全体です。

```
入力: ソースコード
      ↓
┌─────────────────────────────────────┐
│           実行環境                   │
│  ┌─────────┐  ┌─────────┐           │
│  │ Parser  │→│Compiler │           │
│  └─────────┘  └────┬────┘           │
│                    ↓                 │
│  ┌─────────────────────────────────┐│
│  │          VM (エンジン)          ││
│  └─────────────────────────────────┘│
│  + 標準ライブラリ, I/O, メモリ管理   │
└─────────────────────────────────────┘
      ↓
出力: 実行結果 + 副作用(出力など)
```

### SubsetJuliaVM の構成

| コンポーネント | 役割 | VM? |
|--------------|------|-----|
| Parser (Pure Rust) | 構文解析 | ✗ |
| Lowering | CST → Core IR | ✗ |
| Compiler | Core IR → バイトコード | ✗ |
| **vm/** | **バイトコード実行** | **✓** |
| RNG, 配列操作, I/O | サポート機能 | ✗ |
| julia/base/ | Pure Julia 実装 | ✗ |
| base_loader | 起動時の Base 読み込み | ✗ |

### 他のシステムとの比較

| システム | 実行環境 | VM 部分 |
|---------|---------|--------|
| Java | JRE (Java Runtime Environment) | JVM |
| Python | CPython | Python VM (ceval.c) |
| Node.js | Node.js | V8 エンジン |
| **SubsetJuliaVM** | **subset_julia_vm クレート全体** | **vm/ モジュール** |

### SubsetJuliaVM は「コンパイラ」か？

よく聞かれる質問です。正確には：

```
△ Julia コンパイラ      → ネイティブコード生成を連想させるため不正確
○ バイトコードコンパイラ → Core IR → Bytecode の変換は確かにコンパイル
○ Julia サブセット処理系 → 学術的に正確
◎ Julia サブセット VM   → 実行環境全体を指す名前として採用
```

SubsetJuliaVM は**バイトコードコンパイラ + スタックマシン VM** のハイブリッドであり、「Julia サブセット実行環境」が最も正確な表現です。

## パーサー (subset_julia_vm_parser)

SubsetJuliaVM は **Pure Rust パーサー** (`subset_julia_vm_parser`) を使用して Julia コードを構文解析します。C 依存がないため、すべてのプラットフォーム（iOS, macOS, Linux, WebAssembly）で同一のコードが動作します。

### パーサーの特徴

1. **Pure Rust 実装**
   - C 依存なし、完全にポータブル
   - `wasm32-unknown-unknown` でコンパイル可能
   - すべてのプラットフォームで同一コード

2. **Julia 構文の完全カバー**
   - 関数定義（通常形式、短縮形式、ラムダ）
   - 構造体（通常、mutable、パラメトリック）
   - 制御フロー（`if`, `for`, `while`, `try/catch`）
   - Where 句: `function f(x::T) where T`, `where {T, S}`
   - 型パターン: `::Type{T}`（匿名型パラメータ）
   - 修飾演算子: `Base.:-`, `Base.:+`
   - マクロ呼び出し: `@time`, `@assert`, `@show`

3. **CST（Concrete Syntax Tree）の生成**
   - 抽象構文木（AST）ではなく、**具象構文木（CST）**を生成
   - すべてのノードにスパン情報（行・列・バイト位置）付き
   - エラーメッセージで正確な箇所を指摘可能

4. **エラーハンドリング**
   - パースエラーは即座に検出
   - ソース位置付きの明確なエラーメッセージ

### CST の例

**入力 Julia コード**:
```julia
function add(x, y)
    return x + y
end
```

**生成される CST**:
```
source_file
└── function_definition
    ├── identifier: "add"
    ├── parameter_list
    │   ├── identifier: "x"
    │   └── identifier: "y"
    └── body
        └── return_statement
            └── binary_expression
                ├── identifier: "x"
                ├── operator: "+"
                └── identifier: "y"
```

各ノードには以下の情報が含まれます：
- **種類（kind）**: `function_definition`, `identifier`, `binary_expression` など
- **スパン（span）**: ソースコード内の位置（行・列・バイトオフセット）
- **テキスト**: そのノードに対応するソースコードの文字列

### 使用方法

```rust
use subset_julia_vm_parser::Parser;

let source = "function f(x) x^2 end";
let parser = Parser::new(source);
let (cst, errors) = parser.parse();

if errors.is_empty() {
    // CST を処理
}
```

### 設計との整合

SubsetJuliaVM の設計では「**パーサは全構文を受理**」することが重要です：

```
✅ サポート済み構文: パース → Lowering → Core IR → 実行
❌ 未サポート構文: パース → Lowering でエラー（ヒント付き）
```

パーサー自体は「サポートされているか」を判定せず、構文的に正しければ CST を生成します。サポート判定は Lowering 層で行われます。

### パーサーの制限事項

1. **意味解析は行わない**
   - 構文的に正しいかどうかのみ判定
   - 型チェック、未定義変数の検出などは行わない
   - → Lowering 層で意味解析を実装

2. **マクロの展開は行わない**
   - `@macro` は CST ノードとして保持されるが、展開はしない
   - → Lowering 層でマクロを特別処理

3. **動的な構文には対応できない**
   - `eval()` で生成されるコードはパースできない
   - → SubsetJuliaVM では `eval` を未サポートとして扱う

これらの制限は、SubsetJuliaVM の設計（「パーサは全構文を受理、Lowering で判定」）と整合しています。

## アーキテクチャ概要

### 4 層のパイプライン

```
┌─────────────────────────────────────────────────────────┐
│  1. Parser (Pure Rust)                                  │
│     • 全 Julia 構文を CST に変換                        │
│     • スパン情報（行・列・byte offset）を保持           │
│     • 構文エラー以外は必ず成功                          │
│     • C 依存なし、全プラットフォームで同一コード        │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  2. Lowering (CST → Core IR)                            │
│     • サポート済み → Core IR に変換                      │
│     • 未サポート → UnsupportedFeature エラー（スパン付き）│
│     • ここで「動くかどうか」が決まる                      │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  3. Compiler (Core IR → Bytecode)                       │
│     • スタックマシン用のバイトコードを生成                │
│     • 型推論とローカル変数管理（HashMap ベース）          │
│     • 多重ディスパッチ（型特異度計算）                   │
│     • Any 型オペランドのランタイムディスパッチ           │
│     • 命令セット: PushI64, AddF64, Jump, Call, etc.     │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  4. VM (Stack-based Interpreter)                        │
│     • バイトコードを逐次実行                            │
│     • 型付き値スタック（I64, F64, Array, Str, etc.）     │
│     • 決定論的 PRNG（StableRNG/LehmerRNG または Xoshiro256++）│
│     • println() 出力をキャプチャ                         │
│     • 動的型のランタイムディスパッチ命令                  │
└─────────────────────────────────────────────────────────┘
```

### 設計原則

1. **パーサは全構文を受理**
   - Pure Rust パーサーは Julia の全構文をパース
   - マクロ、`using`、`eval` などもノードとして保持
   - 構文エラー以外は必ず CST を生成

2. **Lowering がサポート判定**
   - サポートされていない構文は `UnsupportedFeature` エラー
   - スパン情報付きで、エディタで該当箇所をハイライト可能
   - ヒントメッセージで「なぜ動かないか」を説明

3. **VM は Bytecode だけ知る**
   - 最小限の命令セットで実装
   - 機能追加は Lowering 層と Compiler を拡張するだけ
   - VM 自体は変更不要

4. **エラーは必ずスパン付き**
   - 行・列・byte offset を保持
   - エディタで正確にエラー箇所を表示可能

## 実装の詳細

### 例: `println("Hello World")` の実行

最もシンプルな例で、パイプライン全体を追跡します。

#### Step 1: Parser（構文解析）

```julia
println("Hello World")
```

パーサーが CST（Concrete Syntax Tree）を生成：

```
source_file
└── call_expression
    ├── identifier: "println"
    └── argument_list
        └── string_literal: "\"Hello World\""
```

**重要なポイント**: パーサは「`println` がサポートされているか」を判定しません。構文的に正しければ CST を生成します。

#### Step 2: Lowering（CST → Core IR）

Lowering 層が CST を Core IR に変換：

```rust
Stmt::Expr {
    expr: Expr::Call {
        function: "println",
        args: [
            Expr::Literal(Literal::Str("Hello World"), span)
        ],
        kwargs: [],
        span,
    },
    span,
}
```

**重要なポイント**: `println` は Lowering では特別扱いされず、通常の `Call` として扱われます。コンパイラ層で `println` を特別処理します。もし `@macro` のような未サポート構文なら、`UnsupportedFeature` エラーを返します。

#### Step 3: Compiler（IR → Bytecode）

コンパイラは Core IR をスタックマシン用のバイトコードに変換します。`println("Hello World")` の場合、処理は以下の通りです：

1. **呼び出し式のコンパイル**: `compile_call("println", args)` が `println` をビルトイン関数として検出し、`compile_builtin_call("println", args)` を呼び出します。

2. **各引数のコンパイル**: 各引数について、`compile_builtin_call` は `compile_expr(arg)` を呼び出します。`Expr::Literal(Literal::Str("Hello World"), span)` の場合、`compile_expr` は以下を生成します：
   ```rust
   Instr::PushStr("Hello World".to_string())  // 文字列リテラルをスタックにプッシュ
   ```

3. **型に応じた出力命令の生成**: 各引数をコンパイルした後、`compile_builtin_call` は引数の型をチェックし、対応する出力命令を生成します：
   ```rust
   Instr::PrintStrNoNewline  // スタックから文字列をポップして出力（改行なし）
   ```

4. **改行と戻り値の生成**:
   ```rust
   Instr::PrintNewline       // 改行を出力
   Instr::PushNothing        // nothing をプッシュ（Julia の println は nothing を返す）
   ```

5. **トップレベルの return**: `println("Hello World")` が最後のトップレベル文の場合、`compile_core_program` は `emit_return_for_type(ValueType::Nothing)` を呼び出し、以下を生成します：
   ```rust
   Instr::ReturnNothing      // main から nothing を返す
   ```

**完全なバイトコードシーケンス**:
```rust
[
    Instr::PushStr("Hello World".to_string()),  // compile_expr で文字列リテラル用に生成
    Instr::PrintStrNoNewline,                   // compile_builtin_call で型に基づいて生成
    Instr::PrintNewline,                        // compile_builtin_call で生成
    Instr::PushNothing,                         // compile_builtin_call で生成（戻り値）
    Instr::ReturnNothing,                       // emit_return_for_type でトップレベル用に生成
]
```

**重要なポイント**: `println` は `compile_builtin_call` で特別に処理され、コンパイル時に推論された引数の型に基づいて、型特化の出力命令（`PrintI64NoNewline`, `PrintF64NoNewline`, `PrintStrNoNewline`）を生成します。

#### Step 4: VM（バイトコード実行）

スタックマシンでバイトコードを実行します。VM は `ip`（命令ポインタ）で命令を fetch し、`ip += 1` した後に命令を実行します。

```rust
// VM の状態
struct Vm {
    code: Vec<Instr>,      // バイトコード列
    ip: usize,             // 命令ポインタ
    stack: Vec<Value>,     // 実行スタック
    output: String,        // 出力バッファ
    rng: R,                // 乱数生成器
}

// 実行の流れ（概念）
loop {
    match instr {
        Instr::PushStr(s) => {
            stack.push(Value::Str(s.clone()));
            // スタック: [Str("Hello World")]
        }
        Instr::PrintStrNoNewline => {
            let s = pop_str(&mut stack);  // "Hello World" を取り出す
            output.push_str(&s);          // 出力バッファに追加
            // スタック: []
            // output: "Hello World"
        }
        Instr::PrintNewline => {
            output.push('\n');            // 改行を追加
            // output: "Hello World\n"
        }
        Instr::PushNothing => {
            stack.push(Value::Nothing);   // 戻り値（Julia の println は nothing を返す）
            // スタック: [Nothing]
        }
        Instr::ReturnNothing => {
            // トップレベルの return なので実行終了
            return Value::Nothing;
        }
    }
}
```

**命令ごとの状態遷移（例）**:

```
ip  instr                 stack(before)        stack(after)         output
0   PushStr("Hello World") []                  [Str("Hello World")] ""
1   PrintStrNoNewline      [Str("Hello World")] []                  "Hello World"
2   PrintNewline           []                  []                  "Hello World\n"
3   PushNothing            []                  [Nothing]           "Hello World\n"
4   ReturnNothing          [Nothing]           (return)            "Hello World\n"
```

**実行結果**:
- `output` バッファ: `"Hello World\n"`
- 戻り値: `Value::Nothing`（Julia の `println` は `nothing` を返す）

## Lowering: CST から Core IR への変換

### Lowering とは

**Lowering（低レベル化）** とは、高レベルな構文木（CST）を、より単純で実行可能な中間表現（Core IR）に変換するプロセスです。コンパイラ理論では、このフェーズは「意味解析」と「中間コード生成」に相当します。

SubsetJuliaVM における Lowering の役割：

```
CST (Concrete Syntax Tree)     Core IR (Intermediate Representation)
━━━━━━━━━━━━━━━━━━━━━━━━━━━    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• Julia の全構文を表現          • 最小限のノードセット
• パーサーが生成                • Bytecode に落とし込みやすい形式
• 複雑な構文糖も含む            • 構文糖は展開済み
• サポート可否は不明            • サポート済み構文のみ
```

#### Lowering の具体的な処理内容

Lowering は以下の4つの主要な処理を行います：

1. **構文の認識と分類**
   - CST ノードの種類を判定（`for` ループ、`if` 文、関数呼び出しなど）
   - 各構文がサポートされているかチェック

2. **構文糖の展開（Desugaring）**
   - 暗黙の乗算: `2x` → `2 * x`
   - 範囲の省略: `1:10` → `1:1:10`（step が省略された場合）
   - 配列内包表記: `[x^2 for x in 1:5]` → `Comprehension` ノード

3. **意味的な検証**
   - 未サポート構文の検出（`@macro`, `using`, `eval` など）
   - エラー時にスパン情報とヒントメッセージを生成

4. **Core IR ノードの構築**
   - CST を再帰的に走査し、対応する Core IR ノードを生成
   - スパン情報をすべてのノードに付与

#### Lowering の処理フロー

Lowering は**再帰的な下降パース（recursive descent）**の手法で実装されています：

```rust
// 疑似コード: Lowering の処理フロー
fn lower_program(cst: &CstNode) -> Result<Program, UnsupportedFeature> {
    let mut stmts = Vec::new();

    // CST の各トップレベルノードを処理
    for node in cst.children() {
        match node.kind() {
            "function_definition" => {
                // 関数定義の Lowering
                let func = lower_function(node)?;  // 再帰呼び出し
                stmts.push(Stmt::Function(func));
            }
            "assignment" => {
                // 代入文の Lowering
                let stmt = lower_stmt(node)?;  // 再帰呼び出し
                stmts.push(stmt);
            }
            "macro_call" => {
                // 未サポート構文を検出
                return Err(UnsupportedFeature {
                    kind: MacroCall,
                    span: node.span(),
                    hint: Some("Macro calls are not supported...".to_string()),
                });
            }
            _ => {
                // その他の構文も同様に処理
            }
        }
    }

    Ok(Program { stmts })
}

fn lower_expr(node: &CstNode) -> Result<Expr, UnsupportedFeature> {
    match node.kind() {
        "binary_expression" => {
            // 二項演算: 左辺と右辺を再帰的に Lowering
            let left = lower_expr(node.child("left"))?;   // 再帰
            let right = lower_expr(node.child("right"))?; // 再帰
            Ok(Expr::BinaryOp { op, left, right, span })
        }
        "implicit_multiplication" => {
            // 構文糖の展開: 2x → 2 * x
            let left = lower_expr(node.child("number"))?;
            let right = lower_expr(node.child("variable"))?;
            Ok(Expr::BinaryOp {
                op: BinaryOp::Mul,
                left: Box::new(left),
                right: Box::new(right),
                span: node.span(),
            })
        }
        // ... その他の式ノード
    }
}
```

**重要なポイント**:
- **再帰的処理**: 式の中に式、文の中に文が含まれるため、再帰的に処理
- **エラー伝播**: `?` 演算子で `UnsupportedFeature` エラーを上位に伝播
- **スパン保持**: すべての Core IR ノードに元のソース位置を保持

### なぜ Lowering が重要か

SubsetJuliaVM の設計で最も重要な決定の一つが「**サポート判定を Lowering で行う**」ことです。

```
従来のアプローチ:
  Parser で制限 → 受け付けない構文が多い → ユーザは「なぜ？」と混乱

SubsetJuliaVM のアプローチ:
  Parser は全受理 → Lowering で判定 → 明確なエラーメッセージ
```

この設計のメリット：

1. **明確なエラーメッセージ**: 「この構文は未サポートです」とスパン付きで報告
2. **拡張が容易**: 新機能追加は Lowering を拡張するだけ
3. **関心の分離**: Parser は構文、Lowering は意味を担当

### Core IR: 最小限のノードセット

Core IR は Julia の豊富な構文を、最小限のノードに「脱糖（desugar）」します：

```rust
// 文 (Statement)
enum Stmt {
    Assign { var, value, span }      // x = expr
    For { var, start, end, step, body, span }
    While { condition, body, span }
    If { condition, then_branch, else_branch, span }
    Break { span }
    Continue { span }
    Return { value, span }
    Expr { expr, span }              // 式文
    // ... その他
}

// 式 (Expression)
enum Expr {
    Literal(Literal, Span)           // 42, 3.14, "hello"
    Var(String, Span)                // 変数参照
    BinaryOp { op, left, right, span }
    UnaryOp { op, operand, span }
    Call { function, args, kwargs, span }
    ArrayLiteral { elements, shape, span }
    Index { array, indices, span }
    Range { start, step, stop, span }
    // ... その他
}
```

**設計原則**: Julia 構文 >> Core IR ノード（多対少の関係が健全）。

### Core IR とは何か：設計思想と目的

Core IR（Intermediate Representation）は、**Bytecode に落とし込みやすい最小限の抽象構文**です。Julia の多様な構文を、実行可能な基本操作に抽象化します。

#### なぜ Core IR が必要なのか

SubsetJuliaVM のパイプラインには3つの異なる抽象レベルがあります：

```
┌─────────────────────────────────────────────────────────┐
│  レベル1: CST (Concrete Syntax Tree)                    │
│  • Julia の全構文をそのまま表現                         │
│  • パーサーが生成（構文解析のみ）                        │
│  • 例: `for i in 1:10`, `[x^2 for x in 1:5]`, `2x`    │
│  • 問題: 構文糖が多く、Bytecode に直接変換できない      │
└─────────────────────────────────────────────────────────┘
                        ↓ Lowering
┌─────────────────────────────────────────────────────────┐
│  レベル2: Core IR (Intermediate Representation)         │
│  • 最小限のノードセット（約20種類）                      │
│  • 構文糖は展開済み（`2x` → `2 * x`）                   │
│  • 例: `For { var, start, end, body }`, `BinaryOp`     │
│  • 利点: Bytecode に落としやすい構造、デバッグしやすい  │
└─────────────────────────────────────────────────────────┘
                        ↓ Compiler
┌─────────────────────────────────────────────────────────┐
│  レベル3: Bytecode (実行可能な命令列)                   │
│  • スタックマシン用の命令（PushI64, AddI64, Jump, etc.）│
│  • 線形な命令列（逐次実行可能）                          │
│  • 例: `[PushI64(1), PushI64(2), AddI64, ReturnI64]`  │
│  • 利点: VM が直接実行できる                            │
└─────────────────────────────────────────────────────────┘
```

CST だけでは不十分な理由は「構文として正しい」以上の情報が必要になるためです。CST は文字列と構文の形を保持する一方で、VM が必要とする**意味の正規化**がされていません：

- **構文糖が多すぎる**: `2x` / `for i in` / `do` / ブロードキャストなど、同じ意味が多数の構文で表現される
- **実行に必要な明示性がない**: 代入・暗黙 return・評価順序などが CST だけでは一貫して扱えない
- **サポート判定が曖昧**: 「どの機能を許可するか」を構文レベルではなく意味レベルで判定したい

Core IR はこれらを **少数のノードへ正規化**し、Bytecode に落とし込みやすい形に変換するための中間表現です。

**AST と CST の違い（簡潔版）**:
- **CST (Concrete Syntax Tree)**: 字句・記号・括弧など「書き方の形」を保持する木
- **AST (Abstract Syntax Tree)**: 意味に不要な構文を落とし、演算や構造を抽象化した木

SubsetJuliaVM では、パーサーが出力する **CST** を受け取り、Lowering で **Core IR（独自の中間表現）** に変換します。Core IR は「AST に近い抽象度」を持ちますが、汎用的な AST そのものではありません。構文糖の展開・構文の正規化に加え、Compiler が Bytecode 化しやすい形に落とした**実行寄りの IR**で、`@time`/`@assert`/`@show` のようなマクロは Core IR の専用ノードに変換されます。
つまり **CST →（抽象化）→ AST 的な構造 →（脱糖/正規化）→ Core IR** という位置づけで、Core IR は「汎用的な AST からさらに実行向けに整理された表現」として使われています。

**Core IR の役割**:
1. **抽象化**: Julia の多様な構文を統一的な表現に変換
2. **検証**: サポート済み構文のみが Core IR に変換される（未サポートはエラー）
3. **デバッグ**: 高レベルな構造を保持しているため、問題の特定が容易
4. **拡張性**: 新機能追加時、Core IR にノードを追加するだけで対応可能

#### Core IR とバイトコードの違い

| 特徴 | Core IR | Bytecode |
|-----|---------|----------|
| **構造** | ツリー構造（再帰的） | 線形な命令列 |
| **抽象度** | 高レベル（`For`, `If`, `Call`） | 低レベル（`PushI64`, `Jump`） |
| **可読性** | 高い（Julia に近い） | 低い（機械的） |
| **用途** | 意味解析、検証、デバッグ | 実行 |
| **例** | `For { var: "i", start: ..., end: ... }` | `[PushI64(1), StoreLocal(0), ...]` |

**なぜ2段階に分けるのか**:
- **Core IR は木構造**のため、直接実行すると再帰的な評価になり、評価順序・スタック操作・制御フローが曖昧になる
- **Bytecode は線形命令列**として実行順序とジャンプ先を明示し、VM を「命令ディスパッチ」だけの単純構造にできる
- **Core IR → Bytecode の変換**は型推論や最適化の機会を提供
- **Core IR の段階**で意味的な検証（未定義変数、型エラーなど）が可能
- **デバッグ時**、Core IR の方が問題箇所を特定しやすい

#### Core IR の「Core」の意味

「Core」という名前は、**Julia の Core モジュール**に由来します。Julia の Core モジュールは、言語の最小限の機能を提供します：

```julia
# Julia の Core モジュール（例）
Core.Int64, Core.Float64, Core.String
Core.if, Core.for, Core.while
Core.getfield, Core.setfield!
```

SubsetJuliaVM の Core IR も同様に、**実行に必要な最小限の操作**のみを表現します。Julia の豊富な構文（マクロ、メタプログラミング、高度な型システムなど）は Core IR には含まれず、Lowering の段階で「サポートされていない」と判定されます。

### UnsupportedFeature エラー

未サポートの構文に遭遇すると、Lowering は詳細なエラーを生成します：

```rust
pub struct UnsupportedFeature {
    pub kind: UnsupportedFeatureKind,
    pub span: Span,           // エラー箇所（行・列・バイト位置）
    pub hint: Option<String>, // ユーザへのヒント
}

pub enum UnsupportedFeatureKind {
    MacroCall,              // @macro
    UsingStatement,         // using Package
    ImportStatement,        // import Package
    ExportStatement,        // export func
    AbstractType,           // abstract type
    TypeAlias,              // const T = ...
    WhereClause,            // function f(x::T) where T
    GeneratedFunction,      // @generated
    // ... その他多数
}
```

#### エラー例: マクロ呼び出し

```julia
@info "hello"
```

```
UnsupportedFeature {
    kind: MacroCall,
    span: Span { start: 0, end: 13, start_line: 1, start_column: 1, ... },
    hint: Some("Macro calls are not supported. Only @time, @assert, @show are available."),
}
```

エディタではこのスパン情報を使って、該当箇所をハイライト表示できます。

### Lowering の実装構造

Lowering は再帰的に CST を走査し、各ノードを Core IR に変換します：

```
lowering/
├── mod.rs      # エントリポイント、Program 構築
├── expr.rs     # 式の変換（BinaryOp, Call, Array, etc.）
├── stmt.rs     # 文の変換（Assign, For, If, etc.）
├── function.rs # 関数定義の変換
└── struct_.rs  # 構造体定義の変換
```

#### 主要な関数

```rust
// expr.rs
pub fn lower_expr(walker: &CstWalker, node: Node) -> LowerResult<Expr>

// stmt.rs
pub fn lower_stmt(walker: &CstWalker, node: Node) -> LowerResult<Stmt>

// function.rs
pub fn lower_function(walker: &CstWalker, node: Node) -> LowerResult<Function>
```

`LowerResult<T>` は `Result<T, UnsupportedFeature>` のエイリアスです。

#### Lowering の実際の処理例

具体的な Julia コードがどのように Core IR に変換されるか、ステップバイステップで見てみましょう：

**入力 Julia コード**:
```julia
function add(x, y)
    return x + y
end

result = add(1, 2)
```

**Step 1: Parser が CST を生成**
```
source_file
├── function_definition
│   ├── identifier: "add"
│   ├── parameter_list: ["x", "y"]
│   └── body
│       └── return_statement
│           └── binary_expression
│               ├── identifier: "x"
│               ├── operator: "+"
│               └── identifier: "y"
└── assignment
    ├── identifier: "result"
    └── call_expression
        ├── identifier: "add"
        └── argument_list
            ├── integer_literal: "1"
            └── integer_literal: "2"
```

**Step 2: Lowering が Core IR に変換**

```rust
// function.rs が関数定義を処理
Function {
    name: "add",
    params: vec!["x".to_string(), "y".to_string()],
    body: Block {
        stmts: vec![
            Stmt::Return {
                value: Some(Expr::BinaryOp {
                    op: BinaryOp::Add,
                    left: Box::new(Expr::Var("x".to_string(), span)),
                    right: Box::new(Expr::Var("y".to_string(), span)),
                    span,
                }),
                span,
            }
        ],
        span,
    },
    span,
}

// stmt.rs が代入文を処理
Stmt::Assign {
    var: "result".to_string(),
    value: Expr::Call {
        function: "add".to_string(),
        args: vec![
            Expr::Literal(Literal::Int(1), span),
            Expr::Literal(Literal::Int(2), span),
        ],
        kwargs: vec![],
        span,
    },
    span,
}
```

**Step 3: Compiler がバイトコードに変換**（Lowering の後）

```rust
// 関数定義のバイトコード
[
    LoadLocal(0),      // x をロード
    LoadLocal(1),      // y をロード
    AddI64,            // x + y
    ReturnI64,         // 結果を返す
]

// 呼び出し側のバイトコード
[
    PushI64(1),        // 第1引数
    PushI64(2),        // 第2引数
    Call("add", 2),    // 関数呼び出し
    StoreLocal(0),     // result に保存
]
```

この例から分かること：
- **Lowering は構造を保持**: `x + y` は `BinaryOp` として表現され、まだ実行されていない
- **Compiler が実行形式に変換**: Core IR の `BinaryOp` が `AddI64` 命令になる
- **スパン情報が伝播**: 各段階で元のソース位置が保持される

### スパン情報の保持

すべての Core IR ノードは `Span` を保持します。これにより：

- **エラー報告**: 実行時エラーも正確な位置を報告可能
- **デバッグ**: どの Julia コードがどの IR を生成したか追跡可能
- **IDE 統合**: エディタでのハイライト、ジャンプが可能

`Span` は「元のソースに対する位置情報のスナップショット」です。`start`/`end` は UTF-8 バイトオフセットの半開区間 `[start, end)` を表し、`start_line`/`start_column` は 1-indexed 行・列（列はバイト列）です。同じソース文字列に対して `Span.text(source)` で切り出せる前提のため、エラー表示やハイライトがブレません。

```rust
pub struct Span {
    pub start: usize,        // バイトオフセット（開始）
    pub end: usize,          // バイトオフセット（終了）
    pub start_line: usize,   // 行番号（1-indexed）
    pub end_line: usize,
    pub start_column: usize, // 列番号（1-indexed）
    pub end_column: usize,
}
```

### Lowering と他のフェーズの関係

```
┌─────────────┐
│   Parser    │  → CST を生成（構文のみ判定）
└──────┬──────┘
       │ CST (全 Julia 構文)
       ▼
┌─────────────┐
│  Lowering   │  → サポート判定 + Core IR 生成
└──────┬──────┘
       │ Core IR (サポート済み構文のみ)
       ▼
┌─────────────┐
│  Compiler   │  → バイトコード生成
└──────┬──────┘
       │ Bytecode
       ▼
┌─────────────┐
│     VM      │  → 実行
└─────────────┘
```

**Lowering の責務**:
1. CST → Core IR の変換
2. サポート/未サポートの判定
3. 構文糖の展開（desugar）
4. スパン情報の伝播

**Lowering がやらないこと**:
- 型推論（コンパイラ層が担当）
- 最適化（現在は未実装）
- バイトコード生成（コンパイラ層が担当）

### Lowering の重要性：なぜこの設計が優れているか

SubsetJuliaVM の設計で、**Lowering がサポート判定を行う**という決定は、以下の理由で重要です：

#### 1. ユーザー体験の向上

```
❌ 悪い設計: Parser で制限
  ユーザー: "for i in 1:10 と書いたのに、なぜエラー？"
  システム: "SyntaxError: unexpected token 'for'"
  → ユーザーは混乱（構文的には正しいのに）

✅ 良い設計: Lowering で判定（SubsetJuliaVM）
  ユーザー: "for i in 1:10 と書いた"
  システム: "UnsupportedFeature: for loops are supported, but 'for i in collection' syntax is not yet implemented. Use 'for i in start:end' instead."
  → ユーザーは「何が問題か」「どうすればいいか」を理解できる
```

#### 2. 拡張性

新機能を追加する場合：

```
従来のアプローチ（Parser で制限）:
  1. Parser を修正（構文を受け付ける）
  2. Lowering を修正（Core IR に変換）
  3. Compiler を修正（バイトコード生成）
  4. VM を修正（実行ロジック）
  → 4箇所の変更が必要

SubsetJuliaVM のアプローチ:
  1. Lowering を修正（CST → Core IR の変換を追加）
  2. Compiler を修正（Core IR → Bytecode の変換を追加）
  → 2箇所の変更で済む（Parser と VM は変更不要）
```

#### 3. 関心の分離（Separation of Concerns）

```
┌─────────────┐
│   Parser    │  → 「構文的に正しいか」のみ判定
└─────────────┘
      ↓
┌─────────────┐
│  Lowering   │  → 「意味的にサポートされているか」を判定
└─────────────┘
      ↓
┌─────────────┐
│  Compiler   │  → 「実行可能な形式に変換できるか」を判定
└─────────────┘
      ↓
┌─────────────┐
│     VM      │  → 「実行できるか」を判定（実行時エラー）
└─────────────┘
```

各層が明確な責務を持ち、変更の影響範囲が限定的です。

#### 4. デバッグの容易さ

Core IR は高レベルな構造を保持しているため、問題の特定が容易です：

```
問題: "関数呼び出しでエラーが発生"

❌ バイトコードレベルでのデバッグ:
  [PushI64(1), PushI64(2), Call("add", 2), ...]
  → どの Julia コードに対応するか不明

✅ Core IR レベルでのデバッグ:
  Expr::Call {
      function: "add".to_string(),
      args: vec![
          Expr::Literal(Literal::Int(1), span),
          Expr::Literal(Literal::Int(2), span)
      ],
      kwargs: vec![],
      span: Span { start_line: 5, ... }
  }
  → 元の Julia コード（5行目の add(1, 2)）が明確
```

#### まとめ: Lowering の役割

Lowering は SubsetJuliaVM の**「意味解析エンジン」**です：

1. **構文の意味を理解**: CST の各ノードが「何を意味するか」を解釈
2. **サポート判定**: その意味が VM で実行可能か判定
3. **抽象化**: 実行可能な構文を Core IR という統一的な表現に変換
4. **エラー報告**: 未サポート構文を明確なエラーメッセージで報告

この設計により、SubsetJuliaVM は**拡張しやすく、デバッグしやすく、ユーザーフレンドリーな**システムになっています。

## Compiler: Core IR から Bytecode への変換

### なぜ Core IR を直接実行せず、Bytecode に変換するのか

SubsetJuliaVM は Core IR を直接実行せず、一度 **Bytecode（バイトコード命令列）** に変換してから VM で実行します。この設計選択には明確な理由があります。

#### 構造の違い：木構造 vs 線形命令列

**Core IR は木構造（Tree）**：再帰的なデータ構造で、式の中に式、文の中にブロックが含まれます。

```rust
// Core IR の例：For ループ
Stmt::For {
    var: "i".to_string(),
    start: Expr::Literal(Literal::Int(1), span),
    end: Expr::Literal(Literal::Int(10), span),
    step: None,
    body: Block {
        stmts: vec![
            Stmt::Expr {
                expr: Expr::Call { ... },  // ← 再帰的なネスト
                span,
            }
        ],
        span,
    },
    span,
}
```

**Bytecode は線形命令列（Flat）**：単純な配列で、順番に実行するだけです。

```rust
// Bytecode の例：同じ For ループ
[
    PushI64(1),           // start をスタックに積む
    StoreI64("i"),        // i に代入
    LoadI64("i"),         // ← ループ開始（ip=2）
    PushI64(10),          // end をスタックに積む
    GtI64,                // i > 10 ?
    JumpIfZero(15),       // false なら ip=15（ボディ）へ
    Jump(25),             // true なら ip=25（ループ終了）へ
    // ... ボディの命令（ip=15〜）...
    LoadI64("i"),         // i をロード
    PushI64(1),           // step=1
    AddI64,               // i + 1
    StoreI64("i"),        // i に代入
    Jump(2),              // ← ループ開始（ip=2）に戻る
    // ← ループ終了（ip=25）
]
```

#### 実装の複雑さ：Tree-walking vs Bytecode VM

**Core IR を直接実行する場合（Tree-walking interpreter）**：

```rust
fn eval_stmt(stmt: &Stmt, env: &mut Env) -> Result<(), VmError> {
    match stmt {
        Stmt::For { var, start, end, step, body, .. } => {
            let start_val = eval_expr(start, env)?;  // ← 再帰呼び出し
            let end_val = eval_expr(end, env)?;      // ← 再帰呼び出し
            let step_val = step.as_ref()
                .map(|s| eval_expr(s, env))
                .transpose()?
                .unwrap_or(1);

            let mut i = start_val;
            loop {
                if i > end_val { break; }
                env.set(var, i);
                eval_block(body, env)?;              // ← さらに再帰
                i += step_val;
            }
            Ok(())
        }
        Stmt::Assign { var, value, .. } => {
            let val = eval_expr(value, env)?;        // ← 再帰呼び出し
            env.set(var, val);
            Ok(())
        }
        // ... 他の文も同様に再帰的に評価
    }
}
```

**問題点**：
- **再帰的な関数呼び出しのオーバーヘッド**が大きい（各 `eval_expr`/`eval_stmt` でスタックフレーム生成）
- **制御フローが暗黙的**（ジャンプ先が関数呼び出しに隠蔽される）
- **デバッグが困難**（「今どこを実行しているか」が関数呼び出しスタックに分散）

**Bytecode VM の場合**：

```rust
pub fn run(&mut self) -> Result<Value, VmError> {
    loop {
        let instr = self.code[self.ip].clone();  // 配列アクセス（高速）
        self.ip += 1;                            // IP をインクリメント

        match instr {                            // 単純な分岐
            Instr::PushI64(x) => self.stack.push(Value::I64(x)),
            Instr::AddI64 => {
                let b = pop_i64(&mut self.stack);
                let a = pop_i64(&mut self.stack);
                self.stack.push(Value::I64(a + b));
            }
            Instr::Jump(addr) => {
                self.ip = addr;                  // 明示的なジャンプ
            }
            // ... 他の命令
        }
    }
}
```

**利点**：
- ✅ **単純なループ**で実行可能（再帰なし）
- ✅ **配列アクセス + enum マッチ**だけ（関数呼び出しなし）
- ✅ **IP（命令ポインタ）で実行位置が明確**
- ✅ **ステップ実行やブレークポイントが容易**

#### 実際の変換の複雑さ

**For ループ一つ**を Bytecode に変換するだけでも：

1. **ジャンプ先のラベル管理**：
   - `loop_start`：ループ開始位置
   - `j_positive`：step > 0 の分岐先
   - `j_exit_pos`：step > 0 のときのループ終了判定
   - `j_exit_neg`：step < 0 のときのループ終了判定

2. **パッチング**：
   - `emit(Instr::Jump(usize::MAX))` でダミージャンプを生成
   - 後から `patch_jump(j_positive, negative_check)` でジャンプ先を確定

3. **break/continue のサポート**：
   - `LoopContext` に `exit_patches` と `continue_patches` を保持
   - break/continue 時に適切なジャンプ先にパッチ

4. **step の正負による条件分岐**：
   - step > 0 のとき：`i > end` で終了
   - step < 0 のとき：`i < end` で終了
   - 両方の条件を Bytecode に展開

この複雑な変換により、VM は**単純なループで効率的に実行**できます。

#### 制御フローの明示性

**Core IR**：ジャンプ先が暗黙的
```rust
Stmt::While { condition: Expr::BinaryOp(...), body: Block { ... } }
```
→ 「どこに戻るか」「どこで終了するか」が構造に埋め込まれている

**Bytecode**：ジャンプ先が明示的
```rust
[
    /* ip=10 */ LoadI64("x"),
    /* ip=11 */ PushI64(0),
    /* ip=12 */ GtI64,
    /* ip=13 */ JumpIfZero(25),  // ← 明示的：ip=25 にジャンプ
    // ... ボディ ...
    /* ip=24 */ Jump(10),        // ← 明示的：ip=10 に戻る
    /* ip=25 */ ...              // ← ループ終了
]
```
→ **IP（命令ポインタ）で実行位置が常に明確**

#### 最適化の機会

Bytecode 生成時に以下の最適化が可能：

1. **定数畳み込み**：
   ```rust
   // Core IR: BinaryOp { op: BinaryOp::Add, left: Literal::Int(1), right: Literal::Int(2) }
   // Bytecode: PushI64(3)  // ← コンパイル時に計算
   ```

2. **無駄な命令の削除**：
   ```rust
   // 最適化前: [PushI64(x), Pop]
   // 最適化後: []  // ← 削除
   ```

3. **ジャンプの最適化**：
   ```rust
   // 最適化前: [Jump(5), ..., /* ip=5 */ Jump(10)]
   // 最適化後: [Jump(10), ...]  // ← 直接 ip=10 にジャンプ
   ```

4. **型情報の伝播**：
   ```rust
   // Core IR: Var("x") の型が不明
   // Compiler: locals.get("x") で I64 と確定
   // Bytecode: LoadI64("x")  // ← 型チェック不要
   ```

#### Tree-walking interpreter との性能比較

| 方式 | 実行ループ | オーバーヘッド | 実行速度 |
|-----|----------|------------|---------|
| **Tree-walking** | `eval_stmt()` → `eval_expr()` → ... | 関数呼び出し（スタックフレーム、引数渡し） | 遅い |
| **Bytecode VM** | `loop { match code[ip] { ... } }` | 配列アクセス + enum マッチ | 中程度 |
| **JIT** | ネイティブコード生成 | コンパイル時間 | 速い（iOS では不可） |

SubsetJuliaVM は iOS 制約下で、**Tree-walking より速く、JIT なしで App Store 承認可能**な設計として Bytecode VM を採用しています。

#### まとめ：なぜ Bytecode に変換するのか

```
Core IR を直接実行（Tree-walking）:
  ✗ 再帰的な関数呼び出しのオーバーヘッド
  ✗ 制御フローが暗黙的でデバッグ困難
  ✗ 最適化の機会が少ない

Core IR → Bytecode → VM:
  ✓ 単純なループで実行（関数呼び出しなし）
  ✓ IP で実行位置が明確（デバッグ容易）
  ✓ ジャンプ先が明示的（制御フローが明確）
  ✓ コンパイル時最適化が可能
  ✓ Tree-walking より高速
```

**結論**：Core IR を Bytecode に変換することで、実行効率とデバッグ容易性の両立を実現しています。

## サポートされている機能

### 制御フロー

- `if/elseif/else` 条件分岐
- `for v in start:end` および `for v in start:step:end` ループ
- `for c in "string"`, `for x in array`（ForEach ループ）
- `while condition ... end` ループ
- `break`, `continue`, `return`
- `try/catch/finally` エラーハンドリング（`try/catch e/finally`, `try/catch/else/finally` を含む）

### データ構造

- **1D 配列**: `[1, 2, 3]`, `zeros(n)`, `ones(n)`, `fill(v, n)`, `trues(n)`, `falses(n)`
- **2D 行列**: `zeros(m, n)`, `ones(m, n)`, `fill(v, m, n)`
- **配列内包表記**: `[expr for x in iter]`, `[expr for x in iter if cond]`
- **配列スライス**: `arr[1:5]`, `arr[:]`, `mat[:, :]`, `mat[1:2, :]`
- **範囲**: `1:n`, `start:step:stop`, `range(start, stop; length=N)`
- **タプル**: `(1, 2, 3)`, 分解代入: `a, b = (1, 2)`
- **NamedTuple**: `(x = 1, y = 2)`, フィールドアクセス: `nt.x`
- **Dict**: `Dict("a" => 1)`, `d["key"]`, `d["key"] = v`, `haskey`, `get`, `keys`, `values`, `pairs`, `merge`
- **Generator**（遅延評価）

### 型システム

- **プリミティブ型**: `Int64`, `Float64`, `Bool`, `String`, `Char`, `Nothing`
- **パラメトリック型**: `Complex{T}`, `Rational{T}`, `Array{T}`, カスタムパラメトリック構造体
- **抽象型**: `abstract type Animal end`, `struct Dog <: Mammal`
- **Union 型**: `Union{Int, Float64}`, Union でのサブタイプチェック
- **型階層**: `Any`, `Number`, `Real`, `Integer`, `AbstractFloat`
- **型操作**: `typeof`, `isa`, `convert`, `promote`, `promote_type`, `promote_rule`
- **Type{T} ディスパッチ**: `f(::Type{T}) where T` パターンで型オブジェクトを受け取り

### 演算

- **二項演算**: `+`, `-`, `*`, `/`, `%`, `^`, `//`（有理数）, `÷`（整数除算）
- **比較**: `<`, `>`, `<=`, `>=`, `==`, `!=`
- **同一性/等価性**: `===`（egal）, `!==`, `isequal`（NaN/±0.0 対応）
- **論理演算**: `&&`, `||`（短絡評価）
- **サブタイプ式**: `<:`（例: `Int64 <: Number`）
- **単項演算**: `-x`, `!x`
- **ブロードキャスト**: `.+`, `.-`, `.*`, `./`, `.^`, `.<`, `.>`, `.<=`, `.>=`, `.==`, `.!=`, `.&`, `.|`, `.!`
- **ブロードキャスト代入**: `.+=`, `.-=`, `.*=`, `./=`, `.=`
- **行列演算**: `A * B`（行列乗算）, `transpose()`, `'`（adjoint）

### 関数

- **ユーザ定義関数**: `function f(x, y) ... end`
- **ショート定義**: `f(x) = expr`
- **再帰関数**: 完全サポート
- **複数関数**: 1 ファイルに複数の関数定義可能
- **ラムダ式**: `x -> 2x`, `(x, y) -> x + y`
- **高階関数**: `map`, `filter`, `reduce`, `sum`, `foreach`, `any`, `all`, `count`
- **do 構文**: `map(arr) do x; x^2 end`
- **キーワード引数**: `f(; x=1, y=2)`
- **Where 句**: `function f(x::T) where T ... end`, `function f(x::T) where {T <: Real} ... end`

## iOS 統合

### Swift → Rust ブリッジ

SubsetJuliaVM は Rust で実装され、Swift から C ABI 経由で呼び出されます：

```swift
@_silgen_name("compile_and_run_detailed")
func compile_and_run_detailed(
    _ src: UnsafePointer<CChar>,
    _ seed: UInt64
) -> UnsafeMutablePointer<CExecutionResult>?
```

Rust ライブラリは**静的ライブラリ**（`.a`）としてコンパイルされ、**XCFramework** としてパッケージ化されます：
- `aarch64-apple-ios`（実機用）
- `aarch64-apple-ios-sim`（シミュレータ用）

### エラー報告

エラーは Swift に完全な情報と共に返されます：

- **SyntaxError**: 無効な Julia 構文（パーサレベル、稀）
- **UnsupportedFeature**: 有効な構文だが未実装（Lowering レベル）
  - ソーススパン（行・列）を含む
  - ヒントメッセージを含む
- **RuntimeError**: 実行時エラー（VM レベル）
  - ゼロ除算、インデックス範囲外、未定義変数など

### 決定論的実行

すべての実行は**シード可能な PRNG**を使用します。SubsetJuliaVM は2つの RNG をサポートしています：

- **Xoshiro256++**（Julia のデフォルト RNG）
  - Julia の標準ライブラリ `Random` で使用されるデフォルトアルゴリズム
  - 高速で、小さなメモリフットプリント
  - SHA2-256 ハッシュでシードを拡張（Julia 互換）

- **StableRNG**（LehmerRNG、Julia の StableRNGs.jl 互換）
  - 再現性を重視する場合に使用
  - Julia の StableRNGs.jl と完全互換

現在の実装では、グローバル RNG として `StableRng` を使用していますが、Julia のデフォルトに合わせて `Xoshiro` への移行が検討されています。

- `rand()`, `rand(n)`, `rand(m, n)` は同じシードで同じ結果を生成
- 再現可能なモンテカルロシミュレーションが可能
- 同じコード + 同じシード = 同じ出力

## 実装のハイライト

### 1. 完全に静的なパイプライン

- **JIT なし**: コード生成は一切行わない
- **App Store 準拠**: 動的コード生成による審査拒否のリスクなし
- **予測可能**: コンパイル時にすべてが決定される

### 2. 明確なエラーメッセージ

- **スパン情報**: エラー箇所を正確に特定
- **ヒントメッセージ**: 「なぜ動かないか」を説明
- **3 種類のエラー**: Syntax, Unsupported, Runtime を明確に区別

### 3. 拡張可能な設計

- **機能追加は Lowering 層を拡張するだけ**
- VM 自体は変更不要
- 新しい構文をサポートするのは簡単

### 4. 型安全な実装

- Rust の型システムを活用
- 実行時エラーを最小化
- メモリ安全性を保証

### 5. Pure Julia 実装

- **Complex{T}** と **Rational{T}** を Julia で実装
- **型プロモーションルール**（`promote_rule`, `promote_type`）を Julia で実装
- Base ライブラリ関数（`sum`, `prod`, `gcd`, `lcm` 等）を Julia で実装
- Rust での再実装なしで Julia 互換の動作を実現

### 6. ランタイムディスパッチ

- **多重ディスパッチ**: 型特異度計算
- **ランタイムディスパッチ命令**: Any 型オペランドに対応
- パラメトリック構造体ディスパッチ（`MyStruct{Int64}` が `MyStruct{T}` にマッチ）
- **Union 型**サブタイプチェック

### 7. 動的型付けの保持

- **Julia 準拠の動的型付け**: `x = 1.0; x = 2` の後、`typeof(x)` は `Int64` を返す
- 再代入時に変数の型が適切に更新される
- 混合型の変数（Int64/Float64）に対する不適切な型強制を回避

## 技術選択の検討: なぜこのアーキテクチャか

SubsetJuliaVM のアーキテクチャ（Parser → Lowering → Bytecode → VM）は、iOS 制約下での適切な選択です。ここでは代替アプローチとの比較を行います。

### 代替アプローチの比較

| アプローチ | 実装難度 | 実行速度 | iOS対応 | 拡張性 |
|-----------|---------|---------|---------|-------|
| **① 現在: Bytecode VM** | 中 | 中 | ✓ | 高 |
| ② Tree-walking インタプリタ | 低 | 低 | ✓ | 高 |
| ③ トランスパイラ (→ Swift) | 高 | 高 | ✓ | 低 |
| ④ WASM VM | 中 | 中〜高 | ✓ | 中 |
| ⑤ JIT コンパイル | 高 | 最高 | ✗ | 中 |
| ⑥ レジスタマシン VM | 中〜高 | 中〜高 | ✓ | 高 |

### ① 現在の選択: Bytecode スタックマシン VM

```
Core IR → Bytecode → Stack-based VM
```

**利点**:
- 実装が比較的シンプル
- デバッグしやすい（スタックの状態が明確）
- JIT なしで App Store 対応

**欠点**:
- スタック操作のオーバーヘッド
- ネイティブ実行より遅い

### ② Tree-walking インタプリタ

```
Core IR → 直接実行（再帰的にノードを評価）
```

```rust
fn eval(expr: &Expr, env: &mut Env) -> Value {
    match expr {
        Expr::BinaryOp { op, left, right, .. } => {
            let l = eval(left, env);
            let r = eval(right, env);
            apply_op(op, l, r)
        }
        Expr::Var(name, _) => env.get(name),
        // ...
    }
}
```

**利点**: 実装が最もシンプル、バイトコードコンパイルが不要

**欠点**: **実行が最も遅い**（関数呼び出しオーバーヘッド）

**評価**: 教育目的やプロトタイプには良いが、実用には遅すぎる。

### ③ トランスパイラ (Julia → Swift コード生成)

```
Core IR → Swift ソースコード → Swift コンパイラ → ネイティブ
```

**利点**: **ネイティブ速度で実行**

**欠点**:
- **実行時コンパイルが必要**（ユーザー入力を動的に実行できない）
- REPL が不可能

**評価**: 「ライブラリ」としては使えるが、「インタプリタ」としては使えない

### ④ WASM ベースの実行

```
Core IR → WASM バイトコード → WASM ランタイム
```

**利点**: Web でも iOS でも同じコードが動く

**欠点**: WASM ランタイムの依存、複雑な FFI

**評価**: Web 版 (subset_julia_vm_web) では実際に使用中。iOS では独自 VM の方がシンプル。

### ⑤ JIT コンパイル

```
Core IR → LLVM IR → ネイティブコード（実行時生成）
```

**利点**: **最高の実行速度**（Julia 本体と同じアプローチ）

**欠点**: **iOS App Store で禁止**（動的コード生成不可）

**評価**: iOS では不可能。**これが SubsetJuliaVM を作った理由。**

### ⑥ レジスタマシン VM

```
Core IR → レジスタベース Bytecode → Register-based VM
```

```rust
// スタックマシン（現在）
PushI64(1)
PushI64(2)
AddI64

// レジスタマシン
LoadImm(R0, 1)
LoadImm(R1, 2)
Add(R2, R0, R1)
```

**利点**: スタック操作のオーバーヘッドがない（Lua 5.0+、Android Dalvik で採用）

**欠点**: 実装が複雑（レジスタ割り当て）

**評価**: **将来の最適化候補**。現状ではスタックマシンで十分。

### 現在の選択が適切な理由

```
┌─────────────────────────────────────────────────┐
│  SubsetJuliaVM の目的                                │
│  • 教育・学習用途                               │
│  • Julia 構文の体験                             │
│  • シンプルな数値計算                           │
│                                                 │
│  求められていないこと                            │
│  • 本番環境での高速計算                          │
│  • 大規模データ処理                             │
│  • Julia 本体の置き換え                          │
└─────────────────────────────────────────────────┘
```

1. **iOS App Store 制約**: JIT が使えないため、AOT + VM が必須。
2. **実装の複雑さ**: スタックマシンは実装・デバッグが容易。
3. **拡張性**: Lowering 層での機能追加が容易。
4. **実行速度**: 教育・デモ用途には十分。

### 将来の改善候補

| 改善 | 効果 | 難易度 |
|-----|------|-------|
| レジスタマシン化 | 20-30% 高速化 | 高 |
| 命令の特殊化 | 10-20% 高速化 | 中 |
| インライン化 | ループ高速化 | 中 |
| 定数畳み込み | コンパイル時最適化 | 低 |

**結論**: 現在のアーキテクチャは、これらの目的に対して適切なトレードオフを達成しています。

## まとめ

SubsetJuliaVM は、iOS で Julia のサブセットを実行するための**完全に静的なパイプライン**です。JIT コンパイルを使わず、App Store の審査に通る設計になっています。

**設計の核心**:
- パーサは全構文を受理
- Lowering でサポート判定
- VM は Bytecode だけ知る
- エラーは必ずスパン付き

この設計により、機能追加が容易で、明確なエラーメッセージを提供し、iOS デバイス上で安全に Julia コードを実行できます。
