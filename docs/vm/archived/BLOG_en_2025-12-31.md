This is a technical deep dive into "SubsetJuliaVM", a fully static pipeline that runs a subset of Julia on iOS devices.

## Introduction

### Why build SubsetJuliaVM

Julia is excellent for numerical computing, but running Julia code inside an iOS app is difficult. The reasons:

- **JIT compilation**: Julia generates code at runtime, which does not pass App Store review
- **Huge runtime**: the full Julia runtime is too heavy for iOS apps
- **Dynamic code generation**: may violate security policies

SubsetJuliaVM avoids these constraints and makes it possible to run a **subset** of Julia safely on iOS.

### Why JIT is prohibited on iOS

Here is the reasoning and basis for why JIT compilation and dynamic code generation are prohibited on iOS.

#### 1. App Store Review Guidelines 2.5.2

[App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) explicitly state this in **2.5.2**:

> Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they **download, install, or execute code which introduces or changes features or functionality of the app**, including other apps.

**Summary**: Apps must be self-contained and may not download, install, or execute code that changes app functionality.

#### 2. Technical constraint: W^X (Write XOR Execute)

iOS enforces a **W^X policy** at the kernel level:

| Memory region | Write | Execute | Notes |
|-------------|------|---------|------|
| Code segment | ✗ | ✓ | Execute-only |
| Data segment | ✓ | ✗ | Write-only |
| Required for JIT | ✓ | ✓ | **Not allowed on iOS** |

A JIT compiler needs to execute code that was just written to memory, but iOS forbids this combination. The policy exists for security reasons to prevent malware from generating and executing code at runtime.

#### 3. Exception: specific entitlements

There is an entitlement, [com.apple.security.cs.allow-jit](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.cs.allow-jit), but it has strict limitations:

- **macOS-only** (not usable on iOS)
- Not allowed for App Store distributed apps
- Intended mainly for debuggers and developer tools

#### 4. EU DMA response: BrowserEngineKit (2024-)

As part of the EU Digital Markets Act response, Apple introduced [BrowserEngineKit](https://developer.apple.com/documentation/browserenginekit), which allows JIT, but:

- Available **only in the EU region**
- **Browser engine only** (not general apps)
- Requires a strict review process
- [Reference: Daring Fireball commentary](https://daringfireball.net/2024/06/apple_disables_webkits_jit_in_lockdown_mode)

#### 5. Why Apple bans JIT

```
JIT / dynamic code generation risks:
┌─────────────────────────────────────────────────┐
│  • Malware can generate and execute code at runtime │
│  • Can bypass pre-review of code                 │
│  • May weaken sandbox protections                │
└─────────────────────────────────────────────────┘

Apple's policy:
┌─────────────────────────────────────────────────┐
│  Recommend AOT (Ahead-of-Time) compilation      │
│  → All code can be verified before execution    │
│  → App Store review can verify code safety      │
└─────────────────────────────────────────────────┘
```

#### 6. Impact on SubsetJuliaVM

```
JIT is unavailable
    ↓
Cannot generate native code at runtime
    ↓
AOT (Ahead-of-Time) compilation + a VM (stack-based interpreter) is required
    ↓
SubsetJuliaVM design:
  Parser → Lowering → Compiler (Core IR → Bytecode) → VM (stack-based interpreter)
```

**This is the fundamental reason SubsetJuliaVM is designed as a fully static pipeline.**

### Why "AOT + interpreter"?

#### Three ways to execute code

There are three major ways to run programs:

| Mode | Description | Examples |
|-----|-------------|----------|
| Pure interpreter | Interpret source directly | Early BASIC, shells |
| AOT compilation | Compile to native code ahead of time | C, Rust, Go |
| JIT compilation | Compile to native code at runtime | Julia, Java, V8 |

#### Characteristics of each mode

| Mode | Runtime speed | Startup time | Dynamic code execution | iOS support |
|-----|---------------|--------------|------------------------|-------------|
| Pure interpreter | Slow | Fast | ✓ | ✓ |
| AOT compilation | Fast | Fast | ✗ | ✓ |
| JIT compilation | Fast | Slow | ✓ | **✗** |

#### Options if you want to run user input

SubsetJuliaVM aims to execute Julia code entered by the user.

**Option 1: Pure AOT (impossible)**

```
User input → Compile to native code → Execute
                        ↑
                  Forbidden on iOS (runtime code generation)
```

**Option 2: Precompiled only (restrictive)**

```
During development: Julia code → embedded into the app
At runtime: only embedded code can run
```

Problem: users cannot enter new code. REPL is impossible.

**Option 3: AOT + interpreter (SubsetJuliaVM's choice)**

```
At development (AOT):
  VM itself is compiled from Rust → native code
  (This code is fixed and does not change at runtime)

At runtime (interpreter):
  User input → bytecode → VM interprets
  (No new native code is generated)
```

#### Diagram: JIT vs AOT + interpreter

```
[JIT (prohibited on iOS)]

  User input          JIT compiler         New native code
  "1 + 2"      →    [runtime conversion] → [machine code] → execute
                                              ↑
                                    Write to memory then execute (forbidden)


[AOT + interpreter (SubsetJuliaVM)]

  User input          Bytecode generation        VM (precompiled)
  "1 + 2"      →    [PushI64(1),     →    [interpret]  →  Result: 3
                     PushI64(2),
                     AddI64]
                          ↑                      ↑
                    Treated as data      Compiled ahead of time in Rust
```

#### Is bytecode not "code"?

There is an important distinction:

| | Native code | Bytecode |
|---|---|---|
| Execution | CPU executes directly | VM interprets |
| iOS treatment | Code = review target | Data = OK |
| Runtime generation | **Forbidden** | Allowed |

```
Bytecode = instructions for the VM (data)
Native code = machine code executed directly by the CPU (code)

iOS forbids: runtime generation of native code
iOS allows: generation of bytecode (data)
```

#### Why this is allowed in the App Store

```
SubsetJuliaVM runtime behavior:

  1. User enters Julia code
  2. Parser converts text to CST         ← data structure manipulation
  3. Lowering converts CST to Core IR    ← data structure manipulation
  4. Compiler converts to bytecode       ← data structure manipulation
  5. VM interprets bytecode              ← precompiled code

  → No new native code is generated
  → Everything is handled as data
  → The VM itself is verified during App Store review
```

#### Summary

```
iOS constraint:
  Do not generate or execute native code at runtime

SubsetJuliaVM solution:
  1. VM is compiled to native code ahead of time (AOT)
  2. User input is converted to bytecode (data)
  3. Precompiled VM interprets the bytecode

  → No new native code is generated at runtime
  → App Store constraints are satisfied
  → Users can freely enter and run Julia code
```

### Why a VM is allowed in the App Store

#### Apple Developer Program License Agreement 3.3.2

[Apple Developer Program License Agreement](https://developer.apple.com/programs/information/Apple_Developer_Program_Information_8_12_15.pdf) section **3.3.2** states:

> "Interpreted code may only be used in an Application if **all scripts, code and interpreters are packaged in the Application** and not downloaded."

**Summary**: Interpreters (VMs) and code are allowed as long as they are bundled in the app.

#### Important distinction: executable code vs interpreted code

| Type | Definition | iOS treatment |
|-----|-----------|---------------|
| Executable code | Binary code the CPU can run directly | Download / generation **forbidden** |
| Interpreted code | Code processed by an interpreter | Allowed with conditions |

From [The Register](https://www.theregister.com/2017/06/07/apple_relaxes_developer_rules/):

> "Executable code refers to code that can be run directly – compiled binary files – and interpreted code refers to code that must be processed by an interpreter to generate an executable form."

#### Allowed conditions (June 2017 update)

From [Apple Developer Forums](https://developer.apple.com/forums/thread/52161):

> "Interpreted code may be downloaded to an Application but only so long as such code:
> (a) does not change the primary purpose of the Application
> (b) does not create a store or storefront for other code
> (c) does not bypass signing, sandbox, or other security features of the OS"

#### VM-based apps that are allowed

| App | VM/Interpreter | App Store |
|-----|---------------|-----------|

| Codea | Lua | ✓ Allowed |

| a-Shell | Shell | ✓ Allowed |

These apps are allowed because the VM/interpreter is bundled in the app.

#### Why SubsetJuliaVM is allowed

```
SubsetJuliaVM structure:

  ✓ VM (interpreter) bundled in the app
    → Compiled in Rust → static library (.a)
    → Embedded as an XCFramework

  ✓ User input is treated as interpreted code
    → Converted to bytecode (data)
    → VM interprets it

  ✓ No new executable code is generated
    → No JIT compilation
    → No native code generation

  ✓ App's primary purpose is unchanged
    → Julia execution is declared as the primary purpose
```

#### Checklist for allowed conditions

| Condition | SubsetJuliaVM |
|-----|----------|
| Interpreter is bundled | ✓ Embedded as an XCFramework |
| No downloading executable code | ✓ Bytecode only (data) |
| No generating executable code | ✓ No JIT |

| No bypass of security features | ✓ Runs inside the sandbox |

#### Comparison with Pythonista

```
Pythonista (allowed on the App Store):
  Python interpreter → bundled in the app
  User Python code → executed by the interpreter

SubsetJuliaVM (same structure):
  Julia subset VM → bundled in the app
  User Julia code → executed by the VM

→ Allowed in the same category
```

### Core design

```
Accept all Julia syntax → Decide in Lowering → Execute only Core IR
```

This design ensures:
- **The parser never fails** (if it is syntactically Julia, it passes)
- **Support is decided in Lowering** (clear error messages)
- **The VM only needs to know Core IR** (simple and extensible)

## Terminology: execution environment vs virtual machine

SubsetJuliaVM includes "VM (virtual machine)" in its name, but technically it is an **execution environment**. Here is the distinction.

### Virtual machine (VM) = engine

A **virtual machine** is an interpreter that executes bytecode.
It is best understood as a **software execution engine** that runs intermediate instructions "instead of the CPU".

```
Input: bytecode instructions
      ↓
┌─────────────────────┐
│  Virtual Machine    │
│  • Instruction ptr  │
│  • Stack operations │
│  • Execute ops      │
└─────────────────────┘
      ↓
Output: result
```

In SubsetJuliaVM, `vm.rs` corresponds to this. It executes instructions such as `PushI64(42)` → `AddI64` → `ReturnI64` in sequence.

### Execution environment = the whole vehicle

An **execution environment** is the entire system required to run programs.

```
Input: source code
      ↓
┌─────────────────────────────────────┐
│         Execution Environment       │
│  ┌─────────┐  ┌─────────┐           │
│  │ Parser  │→│Compiler │           │
│  └─────────┘  └────┬────┘           │
│                    ↓                 │
│  ┌─────────────────────────────────┐│
│  │           VM (engine)          ││
│  └─────────────────────────────────┘│
│  + stdlib, I/O, memory management   │
└─────────────────────────────────────┘
      ↓
Output: result + side effects (output, etc.)
```

### SubsetJuliaVM components

| Component | Role | VM? |
|----------|------|-----|
| Parser (Pure Rust) | Syntax parsing | ✗ |
| Lowering | CST → Core IR | ✗ |
| Compiler | Core IR → bytecode | ✗ |
| **vm/** | **Execute bytecode** | **✓** |
| RNG, array operations, I/O | Support functions | ✗ |
| julia/base/ | Pure Julia implementations | ✗ |
| base_loader | Load Base at startup | ✗ |

### Comparison with other systems

| System | Execution environment | VM part |
|--------|------------------------|--------|
| Java | JRE (Java Runtime Environment) | JVM |
| Python | CPython | Python VM (ceval.c) |
| Node.js | Node.js | V8 engine |
| **SubsetJuliaVM** | **entire subset_julia_vm crate** | **vm/ module** |

### Is SubsetJuliaVM a "compiler"?

A common question. More precisely:

```
△ Julia compiler      → inaccurate (implies native code generation)
○ Bytecode compiler   → Core IR → Bytecode is compilation
○ Julia subset system → academically precise
◎ Julia subset VM     → adopted as a name for the full runtime
```

SubsetJuliaVM is a hybrid of a **bytecode compiler + stack-based VM**, and "Julia subset execution environment" is the most accurate description.

## Parser (subset_julia_vm_parser)

SubsetJuliaVM uses **subset_julia_vm_parser**, a Pure Rust parser that can parse all Julia syntax. This section explains its architecture and how it is used.

### Overview

**subset_julia_vm_parser** is a Pure Rust implementation of a Julia parser designed specifically for SubsetJuliaVM. It has no C dependencies and works on all platforms including WebAssembly.

| Feature | Value |
|---------|-------|
| **Language** | Pure Rust |
| **Lexer** | logos (token generation) |
| **Parser** | Recursive descent (Pratt parser for expressions) |
| **Output** | CstNode (Concrete Syntax Tree) |
| **C dependencies** | None |
| **WASM support** | ✅ Native |

### Architecture

```
┌─────────────────────────────────────────┐
│  Source code                            │
│  "function add(x, y) x + y end"         │
└──────────────┬──────────────────────────┘
               │ Lexer (logos)
               ▼
┌─────────────────────────────────────────┐
│  Token stream                           │
│  [Function, Ident("add"), LParen, ...]  │
└──────────────┬──────────────────────────┘
               │ Parser (Recursive descent, Pratt for expressions)
               ▼
┌─────────────────────────────────────────┐
│  CstNode (Concrete Syntax Tree)         │
│  • Full syntax tree for source code     │
│  • Includes span info (line/col/byte)   │
└─────────────────────────────────────────┘
```

### Features

1. **Parses all Julia syntax**
   - Function definitions, control flow, macros, type definitions, etc.
   - Julia 1.x syntax coverage
   - Where clauses: `function f(x::T) where T`, `where {T, S}`
   - Parametric types: `A{T}`, `Dict{K, V}`
   - Broadcast operators: `.+`, `.-`, `.*`, `./`, `.^`
   - Unicode operators and identifiers

2. **No C dependencies**
   - Pure Rust implementation
   - Compiles to WebAssembly without issues
   - Same code runs on native and WASM

3. **Accurate span information**
   - All nodes have precise location info (line/column/byte offset)
   - Error messages can point to exact locations

### Example CST

**Input Julia code**:
```julia
function add(x, y)
    return x + y
end
```

**Generated CST**:
```
SourceFile
└── FunctionDefinition
    ├── identifier: "add"
    ├── ParameterList
    │   ├── identifier: "x"
    │   └── identifier: "y"
    └── body
        └── ReturnStatement
            └── BinaryExpression
                ├── identifier: "x"
                ├── operator: "+"
                └── identifier: "y"
```

Each node includes:
- **Kind**: `FunctionDefinition`, `Identifier`, `BinaryExpression`, etc.
- **Span**: position in source code (line/column/byte offset)
- **Text**: source code substring corresponding to the node

### Why a Pure Rust parser

In SubsetJuliaVM's design, it is critical that **the parser accepts all syntax**. The Pure Rust parser was chosen for several reasons:

| Parser | Characteristics | Usability in SubsetJuliaVM |
|--------|------------------|----------------------------|
| **Pure Rust (subset_julia_vm_parser)** | • Parses all syntax<br>• No C dependencies<br>• WASM compatible | ✅ **Adopted** |
| JuliaSyntax.jl | • Official Julia parser<br>• Most accurate<br>• Implemented in Julia | ❌ Requires Julia runtime (not possible on iOS) |
| tree-sitter-julia | • Fast<br>• Error recovery<br>• C dependencies | ❌ Complex WASM builds |

### How it is used in SubsetJuliaVM

#### 1. Parse source code

```rust
use subset_julia_vm_parser::parse;

let source = "function add(x, y) x + y end";
let cst = parse(source)?;
```

#### 2. Walk the CST

```rust
// subset_julia_vm/src/parser/cst.rs
use subset_julia_vm::parser::{CstWalker, Node, NodeKind};

fn process_node(walker: &CstWalker, node: Node) {
    match walker.kind(&node) {
        NodeKind::FunctionDefinition => {
            // Handle function definitions
        }
        NodeKind::Assignment => {
            // Handle assignments
        }
        _ => {
            // Other nodes
        }
    }

    // Recursively walk child nodes
    for child in walker.named_children(&node) {
        process_node(walker, child);
    }
}
```

### Design alignment

The Pure Rust parser fulfills the design principle that **the parser accepts all syntax**:

```
✅ Supported syntax: parse → Lowering → Core IR
❌ Unsupported syntax: parse → Lowering error
```

The parser itself does not decide "supported or not"; if syntax is valid, it produces a CST. The Lowering layer decides what is supported.

### Limitations

The parser has some inherent limitations that align with SubsetJuliaVM's design:

1. **No semantic analysis**
   - Only checks syntactic correctness
   - Does not perform type checking or undefined variable detection
   - → SubsetJuliaVM implements semantic analysis in the Lowering layer

2. **No macro expansion**
   - `@macro` is preserved as CST nodes, but not expanded
   - → SubsetJuliaVM handles macros specially in Lowering

3. **No dynamic syntax**
   - Code generated by `eval()` cannot be parsed
   - → SubsetJuliaVM treats `eval` as unsupported

### Summary

- **subset_julia_vm_parser**: Pure Rust parser that can parse all Julia syntax
- **No C dependencies**: works on all platforms including WASM
- **Role in SubsetJuliaVM**: convert Julia code to CST; detect syntax errors
- **Design alignment**: fulfills the principle that the parser accepts all syntax

## Architecture overview

### 4-layer pipeline

```
┌─────────────────────────────────────────────────────────┐
│  1. Parser (Pure Rust)                                  │
│     • Converts all Julia syntax to CST                 │
│     • Keeps span info (line/col/byte offset)           │
│     • Always succeeds except for syntax errors         │
│     • No C dependencies, works on all platforms        │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  2. Lowering (CST → Core IR)                            │
│     • Supported → converted to Core IR                 │
│     • Unsupported → UnsupportedFeature error (with span)│
│     • Decides "whether it runs" here                   │
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  3. Compiler (Core IR → Bytecode)                       │
│     • Generates stack-based bytecode                   │
│     • Type inference and locals (HashMap-based)        │
│     • Multiple dispatch with type specificity          │
│     • Runtime dispatch for Any-typed operands          │
│     • Instruction set: PushI64, AddF64, Jump, Call, etc.│
└─────────────────────────────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  4. VM (Stack-based Interpreter)                        │
│     • Executes bytecode sequentially                   │
│     • Typed value stack (I64, F64, Array, Str, etc.)    │
│     • Deterministic PRNG (StableRNG/LehmerRNG or Xoshiro256++)│
│     • Captures println() output                         │
│     • Runtime dispatch instructions for dynamic types  │
└─────────────────────────────────────────────────────────┘
```

### Design principles

1. **The parser accepts all syntax**
   - The Pure Rust parser parses all Julia syntax
   - Macros, `using`, `eval`, etc. are preserved as nodes
   - Always produces a CST unless there is a syntax error

2. **Lowering decides support**
   - Unsupported syntax becomes an `UnsupportedFeature` error
   - Includes span info, so editors can highlight the location
   - Hint messages explain "why it doesn't work"

3. **The VM only needs Core IR**
   - Implemented with a minimal instruction set
   - Feature additions only extend the Lowering layer
   - The VM itself does not need to change

4. **Errors always include spans**
   - Line/column/byte offsets are preserved
   - Editors can show precise error locations

## Implementation details

### Example: executing `println("Hello World")`

We trace the entire pipeline using the simplest example.

#### Step 1: Parser (syntax parsing)

```julia
println("Hello World")
```

The parser generates the CST (Concrete Syntax Tree):

```
source_file
└── call_expression
    ├── identifier: "println"
    └── argument_list
        └── string_literal: "\"Hello World\""
```

**Key point**: the parser does not decide whether `println` is supported. If it is syntactically valid, it produces a CST.

#### Step 2: Lowering (CST → Core IR)

The Lowering layer converts the CST to Core IR:

```rust
Stmt::Expr {
    expr: Expr::Call {
        function: "println",
        args: [
            Expr::Literal(Literal::Str("Hello World"), span)
        ],
        kwargs: [],
        span,
    },
    span,
}
```

**Key point**: `println` is not treated specially in Lowering; it remains a normal `Call`. The compiler layer handles `println` specially. If it were unsupported syntax like a macro call, it would return an `UnsupportedFeature` error.

#### Step 3: Compiler (IR → Bytecode)

The compiler converts Core IR to stack-based bytecode. For `println("Hello World")`, the process is:

1. **Compile the call expression**: `compile_call("println", args)` detects `println` as a builtin and calls `compile_builtin_call("println", args)`.

2. **Compile each argument**: For each argument, `compile_builtin_call` calls `compile_expr(arg)`. For `Expr::Literal(Literal::Str("Hello World"), span)`, `compile_expr` emits:
   ```rust
   Instr::PushStr("Hello World".to_string())  // Push string literal onto stack
   ```

3. **Emit type-specific print instructions**: After compiling each argument, `compile_builtin_call` checks the argument's type and emits the corresponding print instruction:
   ```rust
   Instr::PrintStrNoNewline  // Pop string from stack and print (no newline)
   ```

4. **Emit newline and return value**:
   ```rust
   Instr::PrintNewline       // Print newline
   Instr::PushNothing        // Push nothing (Julia's println returns nothing)
   ```

5. **Top-level return**: If `println("Hello World")` is the last top-level statement, `compile_core_program` calls `emit_return_for_type(ValueType::Nothing)`, which emits:
   ```rust
   Instr::ReturnNothing      // Return nothing from main
   ```

**Complete bytecode sequence**:
```rust
[
    Instr::PushStr("Hello World".to_string()),  // Generated by compile_expr for string literal
    Instr::PrintStrNoNewline,                   // Generated by compile_builtin_call based on type
    Instr::PrintNewline,                        // Generated by compile_builtin_call
    Instr::PushNothing,                         // Generated by compile_builtin_call (return value)
    Instr::ReturnNothing,                       // Generated by emit_return_for_type for top-level
]
```

**Key point**: `println` is handled specially in `compile_builtin_call` and emits type-specific print instructions (`PrintI64NoNewline`, `PrintF64NoNewline`, `PrintStrNoNewline`) based on the argument types inferred during compilation.

#### Step 4: VM (bytecode execution)

The stack-based VM executes bytecode. The VM fetches the instruction at `ip`, increments `ip += 1`, then executes.

```rust
// VM state
struct Vm {
    code: Vec<Instr>,      // Bytecode
    ip: usize,             // Instruction pointer
    stack: Vec<Value>,     // Execution stack
    output: String,        // Output buffer
    rng: R,                // RNG
}

// Execution flow (conceptual)
loop {
    match instr {
        Instr::PushStr(s) => {
            stack.push(Value::Str(s.clone()));
            // Stack: [Str("Hello World")]
        }
        Instr::PrintStrNoNewline => {
            let s = pop_str(&mut stack);  // Pop "Hello World"
            output.push_str(&s);          // Append to output buffer
            // Stack: []
            // output: "Hello World"
        }
        Instr::PrintNewline => {
            output.push('\n');            // Append newline
            // output: "Hello World\n"
        }
        Instr::PushNothing => {
            stack.push(Value::Nothing);   // Return value (println returns nothing)
            // Stack: [Nothing]
        }
        Instr::ReturnNothing => {
            // Top-level return, end execution
            return Value::Nothing;
        }
    }
}
```

**State transitions per instruction (example)**:

```
ip  instr                 stack(before)        stack(after)         output
0   PushStr("Hello World") []                  [Str("Hello World")] ""
1   PrintStrNoNewline      [Str("Hello World")] []                  "Hello World"
2   PrintNewline           []                  []                  "Hello World\n"
3   PushNothing            []                  [Nothing]           "Hello World\n"
4   ReturnNothing          [Nothing]           (return)            "Hello World\n"
```

**Execution result**:
- `output` buffer: `"Hello World\n"`
- Return value: `Value::Nothing` (Julia's `println` returns `nothing`)

## Lowering: converting CST to Core IR

### What is Lowering

**Lowering** is the process of converting a high-level syntax tree (CST) into a simpler, executable intermediate representation (Core IR). In compiler theory, this phase corresponds to "semantic analysis" and "intermediate code generation".

Role of Lowering in SubsetJuliaVM:

```
CST (Concrete Syntax Tree)     Core IR (Intermediate Representation)
━━━━━━━━━━━━━━━━━━━━━━━━━━━    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• Represents all Julia syntax  • Minimal node set
• Generated by the parser      • Form the VM can understand
• Includes complex sugar       • Sugar expanded
• Support unknown              • Supported syntax only
```

#### What Lowering actually does

Lowering performs four major tasks:

1. **Recognize and classify syntax**
   - Determine CST node kinds (`for` loops, `if` statements, function calls, etc.)
   - Check whether each construct is supported

2. **Desugar syntax**
   - Implicit multiplication: `2x` → `2 * x`
   - Range shorthand: `1:10` → `1:1:10` (if step omitted)
   - Array comprehension: `[x^2 for x in 1:5]` → `Comprehension` node

3. **Semantic validation**
   - Detect unsupported syntax (`@macro`, `using`, `eval`, etc.)
   - Generate span info and hint messages on errors

4. **Build Core IR nodes**
   - Walk the CST recursively and produce corresponding Core IR nodes
   - Attach span info to all nodes

#### Lowering flow

Lowering is implemented with **recursive descent**:

```rust
// Pseudocode: Lowering flow
fn lower_program(cst: &CstNode) -> Result<Program, UnsupportedFeature> {
    let mut stmts = Vec::new();

    // Process each top-level CST node
    for node in cst.children() {
        match node.kind() {
            "function_definition" => {
                // Lower function definition
                let func = lower_function(node)?;  // Recursive call
                stmts.push(Stmt::Function(func));
            }
            "assignment" => {
                // Lower assignment
                let stmt = lower_stmt(node)?;  // Recursive call
                stmts.push(stmt);
            }
            "macro_call" => {
                // Detect unsupported syntax
                return Err(UnsupportedFeature {
                    kind: MacroCall,
                    span: node.span(),
                    hint: Some("Macro calls are not supported...".to_string()),
                });
            }
            _ => {
                // Handle other syntax similarly
            }
        }
    }

    Ok(Program { stmts })
}

fn lower_expr(node: &CstNode) -> Result<Expr, UnsupportedFeature> {
    match node.kind() {
        "binary_expression" => {
            // Binary op: lower left/right recursively
            let left = lower_expr(node.child("left"))?;   // Recursion
            let right = lower_expr(node.child("right"))?; // Recursion
            Ok(Expr::BinaryOp { op, left, right, span })
        }
        "implicit_multiplication" => {
            // Desugar: 2x → 2 * x
            let left = lower_expr(node.child("number"))?;
            let right = lower_expr(node.child("variable"))?;
            Ok(Expr::BinaryOp {
                op: Mul,
                left,
                right,
                span: node.span(),
            })
        }
        // ... other expression nodes
    }
}
```

**Key points**:
- **Recursive processing**: expressions contain expressions, statements contain statements
- **Error propagation**: `?` propagates `UnsupportedFeature` errors
- **Span preservation**: all Core IR nodes keep original source locations

### Why Lowering is important

One of the most important decisions in SubsetJuliaVM is to **decide support in Lowering**.

```
Traditional approach:
  Restrict in the parser → many valid syntax rejected → users confused

SubsetJuliaVM approach:
  Parser accepts all → Lowering decides → clear error messages
```

Benefits:

1. **Clear error messages**: "This syntax is unsupported" with spans
2. **Easy to extend**: add features by extending Lowering
3. **Separation of concerns**: parser handles syntax, Lowering handles semantics

### Core IR: minimal node set

Core IR desugars Julia's rich syntax into a small set of nodes:

```rust
// Statements
enum Stmt {
    Assign { var, value, span }      // x = expr
    For { var, start, end, step, body, span }
    While { condition, body, span }
    If { condition, then_branch, else_branch, span }
    Break { span }
    Continue { span }
    Return { value, span }
    Expr { expr, span }              // expression statement
    // ... others
}

// Expressions
enum Expr {
    Literal(Literal, Span)           // 42, 3.14, "hello"
    Var(String, Span)                // variable reference
    BinaryOp { op, left, right, span }
    UnaryOp { op, operand, span }
    Call { function, args, kwargs, span }
    ArrayLiteral { elements, shape, span }
    Index { array, indices, span }
    Range { start, step, stop, span }
    // ... others
}
```

**Design principle**: Julia syntax >> Core IR nodes (a healthy many-to-few relationship).

### What is Core IR: design philosophy and purpose

Core IR (Intermediate Representation) is the **minimal abstract syntax the VM can understand**. It abstracts Julia's diverse syntax into executable primitives.

#### Why Core IR is needed

SubsetJuliaVM's pipeline has three distinct abstraction levels:

```
┌─────────────────────────────────────────────────────────┐
│  Level 1: CST (Concrete Syntax Tree)                    │
│  • Represents all Julia syntax as-is                    │
│  • Generated by the parser (syntax only)                │
│  • Examples: `for i in 1:10`, `[x^2 for x in 1:5]`, `2x`│
│  • Problem: too much syntactic sugar for the VM         │
└─────────────────────────────────────────────────────────┘
                        ↓ Lowering
┌─────────────────────────────────────────────────────────┐
│  Level 2: Core IR (Intermediate Representation)         │
│  • Minimal node set (~20 kinds)                         │
│  • Sugar expanded (`2x` → `2 * x`)                      │
│  • Examples: `For { var, start, end, body }`, `BinaryOp`│
│  • Benefit: structure the VM can understand             │
└─────────────────────────────────────────────────────────┘
                        ↓ Compiler
┌─────────────────────────────────────────────────────────┐
│  Level 3: Bytecode (executable instruction sequence)    │
│  • Stack-machine instructions (PushI64, AddI64, Jump, etc.)│
│  • Linear instruction stream (sequential)               │
│  • Example: `[PushI64(1), PushI64(2), AddI64, ReturnI64]`│
│  • Benefit: directly executable by the VM               │
└─────────────────────────────────────────────────────────┘
```

CST alone is insufficient because the VM needs **semantic normalization** beyond syntactic correctness:

- **Too much syntax sugar**: `2x` / `for i in` / `do` / broadcasting, etc. all express the same meaning in different forms
- **Insufficient execution explicitness**: assignment, implicit returns, evaluation order are not uniform in CST
- **Ambiguous support decisions**: want to decide allowed features at the semantic level, not at syntax

Core IR **normalizes** these into a small set of nodes and converts them into a form the VM can understand.

**CST vs AST (brief)**:
- **CST (Concrete Syntax Tree)**: retains lexical/formatting details like tokens and parentheses
- **AST (Abstract Syntax Tree)**: drops unnecessary syntax and abstracts operations and structure

SubsetJuliaVM takes the **CST** from the parser and converts it into **Core IR (its own IR)** via Lowering. Core IR has AST-like abstraction but is not a generic AST. Beyond desugaring and normalization, it is tailored to be easy for the VM to execute. Macros such as `@time`/`@assert`/`@show` are converted into dedicated Core IR nodes.
In short: **CST → (abstraction) → AST-like structure → (desugar/normalize) → Core IR**. Core IR is an execution-oriented representation refined beyond a generic AST.

**Roles of Core IR**:
1. **Abstraction**: unify diverse Julia syntax into a consistent representation
2. **Validation**: only supported syntax becomes Core IR (unsupported becomes errors)
3. **Debugging**: retains high-level structure to locate problems
4. **Extensibility**: add new features by adding Core IR nodes

#### Core IR vs bytecode

| Feature | Core IR | Bytecode |
|--------|---------|----------|
| **Structure** | Tree (recursive) | Linear instruction stream |
| **Abstraction** | High-level (`For`, `If`, `Call`) | Low-level (`PushI64`, `Jump`) |
| **Readability** | High (close to Julia) | Low (mechanical) |
| **Purpose** | Semantic analysis, validation, debugging | Execution |
| **Example** | `For { var: "i", start: ..., end: ... }` | `[PushI64(1), StoreLocal(0), ...]` |

**Why split into two stages**:
- **Core IR is tree-structured**; executing it directly yields recursive evaluation with unclear order and control flow
- **Bytecode is linear**, making execution order and jump targets explicit and letting the VM be a simple dispatch loop
- **Core IR → Bytecode conversion** provides opportunities for type inference and optimization
- **Core IR stage** enables semantic validation (undefined variables, type errors, etc.)
- **Debugging** is easier at Core IR than bytecode

#### What "Core" means in Core IR

The name "Core" comes from **Julia's Core module**, which provides the minimal language features:

```julia
# Julia Core module (examples)
Core.Int64, Core.Float64, Core.String
Core.if, Core.for, Core.while
Core.getfield, Core.setfield!
```

SubsetJuliaVM's Core IR likewise expresses **only the minimal operations needed to run**. Rich Julia features (macros, metaprogramming, advanced type systems, etc.) are not included and are deemed unsupported during Lowering.

### Lowering implementation structure

Lowering walks the CST recursively and converts each node into Core IR:

```
lowering/
├── mod.rs        # Entry point, Program construction
├── expr.rs       # Expression conversion (BinaryOp, Call, Array, etc.)
├── stmt/         # Statement conversion (modularized)
│   ├── mod.rs
│   ├── assignment.rs
│   ├── control_if.rs
│   ├── control_for.rs
│   ├── control_while.rs
│   ├── control_try.rs
│   └── macros.rs
├── function.rs   # Function definition conversion
├── struct_.rs    # Struct definition conversion
└── abstract_.rs  # Abstract type conversion
```

#### Key functions

```rust
// expr.rs
pub fn lower_expr(walker: &CstWalker, node: Node) -> LowerResult<Expr>

// stmt.rs
pub fn lower_stmt(walker: &CstWalker, node: Node) -> LowerResult<Stmt>

// function.rs
pub fn lower_function(walker: &CstWalker, node: Node) -> LowerResult<Function>
```

`LowerResult<T>` is an alias for `Result<T, UnsupportedFeature>`.

#### Step-by-step Lowering example

Let's walk through how Julia code is converted into Core IR step by step:

**Input Julia code**:
```julia
function add(x, y)
    return x + y
end

result = add(1, 2)
```

**Step 1: Parser generates CST**
```
source_file
├── function_definition
│   ├── identifier: "add"
│   ├── parameter_list: ["x", "y"]
│   └── body
│       └── return_statement
│           └── binary_expression
│               ├── identifier: "x"
│               ├── operator: "+"
│               └── identifier: "y"
└── assignment
    ├── identifier: "result"
    └── call_expression
        ├── identifier: "add"
        └── argument_list
            ├── integer_literal: "1"
            └── integer_literal: "2"
```

**Step 2: Lowering converts to Core IR**

```rust
// function.rs handles function definitions
Function {
    name: "add",
    params: vec!["x".to_string(), "y".to_string()],
    body: Block {
        stmts: vec![
            Stmt::Return {
                value: Some(Expr::BinaryOp {
                    op: BinaryOp::Add,
                    left: Box::new(Expr::Var("x".to_string(), span)),
                    right: Box::new(Expr::Var("y".to_string(), span)),
                    span,
                }),
                span,
            }
        ],
        span,
    },
    span,
}

// stmt.rs handles assignments
Stmt::Assign {
    var: "result".to_string(),
    value: Expr::Call {
        function: "add".to_string(),
        args: vec![
            Expr::Literal(Literal::Int(1), span),
            Expr::Literal(Literal::Int(2), span),
        ],
        kwargs: vec![],
        span,
    },
    span,
}
```

**Step 3: Compiler converts to bytecode** (after Lowering)

```rust
// Bytecode for function definition
[
    LoadLocal(0),      // load x
    LoadLocal(1),      // load y
    AddI64,            // x + y
    ReturnI64,         // return result
]

// Bytecode for call site
[
    PushI64(1),        // 1st arg
    PushI64(2),        // 2nd arg
    Call("add", 2),    // call function
    StoreLocal(0),     // store in result
]
```

What this example shows:
- **Lowering preserves structure**: `x + y` is represented as `BinaryOp`, not executed yet
- **Compiler converts to executable form**: Core IR `BinaryOp` becomes `AddI64`
- **Span info is preserved**: each stage carries source locations

### Preserving span info

All Core IR nodes keep a `Span`. This enables:

- **Error reporting**: runtime errors can report precise locations
- **Debugging**: trace which Julia code generated which IR
- **IDE integration**: highlight and jump to exact locations

`Span` is a snapshot of the original source position. `start`/`end` represent half-open UTF-8 byte offsets `[start, end)`, and `start_line`/`start_column` are 1-indexed line/column numbers (columns are byte offsets). Since `Span.text(source)` can be sliced from the original string, error display and highlights remain stable.

```rust
pub struct Span {
    pub start: usize,        // Byte offset (start)
    pub end: usize,          // Byte offset (end)
    pub start_line: usize,   // Line number (1-indexed)
    pub end_line: usize,
    pub start_column: usize, // Column number (1-indexed)
    pub end_column: usize,
}
```

### Relationship with other phases

```
┌─────────────┐
│   Parser    │  → Generates CST (syntax only)
└──────┬──────┘
       │ CST (all Julia syntax)
       ▼
┌─────────────┐
│  Lowering   │  → Support check + Core IR
└──────┬──────┘
       │ Core IR (supported syntax only)
       ▼
┌─────────────┐
│  Compiler   │  → Bytecode generation
└──────┬──────┘
       │ Bytecode
       ▼
┌─────────────┐
│     VM      │  → Execute
└─────────────┘
```

**Lowering responsibilities**:
1. CST → Core IR conversion
2. Decide supported/unsupported syntax
3. Desugar syntax
4. Propagate span info

**What Lowering does not do**:
- Type inference (handled by the Compiler)
- Optimization (currently unimplemented)
- Bytecode generation (handled by the Compiler)

### Why this design is better

The decision to **decide support in Lowering** is crucial for these reasons:

#### 1. Better user experience

```
❌ Bad design: restrict in parser
  User: "I wrote for i in 1:10, why is it an error?"
  System: "SyntaxError: unexpected token 'for'"
  → Confusing (syntax was valid)

✅ Good design: decide in Lowering (SubsetJuliaVM)
  User: "I wrote for i in 1:10"
  System: "UnsupportedFeature: for loops are supported, but 'for i in collection' syntax is not yet implemented. Use 'for i in start:end' instead."
  → User understands what's wrong and how to fix it
```

#### 2. Extensibility

When adding new features:

```
Traditional approach (restrict in parser):
  1. Modify parser (accept syntax)
  2. Modify Lowering (convert to Core IR)
  3. Modify Compiler (generate bytecode)
  4. Modify VM (execution logic)
  → Changes in 4 places

SubsetJuliaVM approach:
  1. Modify Lowering (add CST → Core IR conversion)
  2. Modify Compiler (add Core IR → Bytecode conversion)
  → Only 2 places (parser and VM unchanged)
```

#### 3. Separation of concerns

```
┌─────────────┐
│   Parser    │  → Only checks "syntax is valid"
└─────────────┘
      ↓
┌─────────────┐
│  Lowering   │  → Checks "semantically supported"
└─────────────┘
      ↓
┌─────────────┐
│  Compiler   │  → Checks "convertible to executable form"
└─────────────┘
      ↓
┌─────────────┐
│     VM      │  → Checks "can execute" (runtime errors)
└─────────────┘
```

Each layer has a clear responsibility and limited change impact.

#### 4. Easier debugging

Core IR retains high-level structure, making it easier to pinpoint issues:

```
Problem: "error during function call"

❌ Bytecode-level debugging:
  [PushI64(1), PushI64(2), Call("add", 2), ...]
  → Hard to map back to Julia code

✅ Core IR-level debugging:
  Expr::Call {
      function: "add",
      args: [Expr::Literal(Int(1)), Expr::Literal(Int(2))],
      span: Span { start_line: 5, ... }
  }
  → Clearly points to the Julia code (line 5: add(1, 2))
```

#### Summary: Lowering's role

Lowering is SubsetJuliaVM's **semantic analysis engine**:

1. **Understands syntax meaning**: interprets what each CST node represents
2. **Decides support**: determines whether the meaning can be executed by the VM
3. **Abstracts**: converts executable syntax into Core IR
4. **Reports errors**: reports unsupported syntax with clear messages

This design makes SubsetJuliaVM **extensible, debuggable, and user-friendly**.

## Compiler: converting Core IR to Bytecode

### Why convert Core IR to Bytecode instead of executing it directly

SubsetJuliaVM does not execute Core IR directly. It first converts it into **Bytecode (instruction sequences)** and then runs it in the VM. This design choice has clear reasons.

#### Structural difference: tree vs linear

**Core IR is a tree**: a recursive structure where expressions contain expressions and statements contain blocks.

```rust
// Core IR example: For loop
Stmt::For {
    var: "i",
    start: Expr::Literal(Int(1), span),
    end: Expr::Literal(Int(10), span),
    step: None,
    body: Block {
        stmts: [
            Stmt::Expr {
                expr: Expr::Call { ... },  // ← recursive nesting
                span,
            }
        ],
        span,
    },
    span,
}
```

**Bytecode is linear**: a simple array executed in order.

```rust
// Bytecode example: same For loop
[
    PushI64(1),           // push start to stack
    StoreI64("i"),        // assign to i
    LoadI64("i"),         // ← loop start (ip=2)
    PushI64(10),          // push end
    GtI64,                // i > 10 ?
    JumpIfZero(15),       // false → ip=15 (body)
    Jump(25),             // true → ip=25 (loop end)
    // ... body instructions (ip=15~)...
    LoadI64("i"),         // load i
    PushI64(1),           // step=1
    AddI64,               // i + 1
    StoreI64("i"),        // assign to i
    Jump(2),              // back to loop start (ip=2)
    // ← loop end (ip=25)
]
```

#### Implementation complexity: tree-walking vs Bytecode VM

**If Core IR is executed directly (tree-walking interpreter)**:

```rust
fn eval_stmt(stmt: &Stmt, env: &mut Env) -> Result<(), VmError> {
    match stmt {
        Stmt::For { var, start, end, step, body, .. } => {
            let start_val = eval_expr(start, env)?;  // recursive call
            let end_val = eval_expr(end, env)?;      // recursive call
            let step_val = step.as_ref()
                .map(|s| eval_expr(s, env))
                .transpose()?
                .unwrap_or(1);

            let mut i = start_val;
            loop {
                if i > end_val { break; }
                env.set(var, i);
                eval_block(body, env)?;              // deeper recursion
                i += step_val;
            }
            Ok(())
        }
        Stmt::Assign { var, value, .. } => {
            let val = eval_expr(value, env)?;        // recursive call
            env.set(var, val);
            Ok(())
        }
        // ... other statements are evaluated recursively
    }
}
```

**Problems**:
- **High overhead from recursive calls** (stack frames for each `eval_expr`/`eval_stmt`)
- **Implicit control flow** (jump targets hidden in function calls)
- **Hard to debug** ("where am I now?" scattered across call stack)

**With a Bytecode VM**:

```rust
pub fn run(&mut self) -> Result<Value, VmError> {
    loop {
        let instr = self.code[self.ip].clone();  // array access (fast)
        self.ip += 1;                            // increment IP

        match instr {                            // simple dispatch
            Instr::PushI64(x) => self.stack.push(Value::I64(x)),
            Instr::AddI64 => {
                let b = pop_i64(&mut self.stack);
                let a = pop_i64(&mut self.stack);
                self.stack.push(Value::I64(a + b));
            }
            Instr::Jump(addr) => {
                self.ip = addr;                  // explicit jump
            }
            // ... other instructions
        }
    }
}
```

**Advantages**:
- ✅ **Simple loop execution** (no recursion)
- ✅ **Only array access + enum match** (no function calls)
- ✅ **Execution position is clear via IP**
- ✅ **Easy to step or set breakpoints**

#### Complexity of the conversion

Converting **just one For loop** to bytecode requires:

1. **Jump label management**:
   - `loop_start`: loop start position
   - `j_positive`: branch for step > 0
   - `j_exit_pos`: exit check for step > 0
   - `j_exit_neg`: exit check for step < 0

2. **Patching**:
   - Emit a dummy jump with `emit(Instr::Jump(usize::MAX))`
   - Later patch with `patch_jump(j_positive, negative_check)`

3. **Support for break/continue**:
   - `LoopContext` keeps `exit_patches` and `continue_patches`
   - Patch to the correct jump target on break/continue

4. **Branching on step sign**:
   - step > 0: exit when `i > end`
   - step < 0: exit when `i < end`
   - both conditions expanded to bytecode

This complexity enables the VM to execute loops efficiently with a simple run loop.

#### Explicit control flow

**Core IR**: jump targets are implicit
```rust
Stmt::While { condition: Expr::BinaryOp(...), body: Block { ... } }
```
→ "where to jump back" and "where to exit" are embedded in structure

**Bytecode**: jump targets are explicit
```rust
[
    /* ip=10 */ LoadI64("x"),
    /* ip=11 */ PushI64(0),
    /* ip=12 */ GtI64,
    /* ip=13 */ JumpIfZero(25),  // ← explicit: jump to ip=25
    // ... body ...
    /* ip=24 */ Jump(10),        // ← explicit: jump back to ip=10
    /* ip=25 */ ...              // ← loop end
]
```
→ **Execution position is always clear via IP**

#### Optimization opportunities

The bytecode generation phase allows optimizations such as:

1. **Constant folding**:
   ```rust
   // Core IR: BinaryOp { op: Add, left: Literal(1), right: Literal(2) }
   // Bytecode: PushI64(3)  // ← computed at compile time
   ```

2. **Dead instruction elimination**:
   ```rust
   // Before: [PushI64(x), Pop]
   // After: []  // ← removed
   ```

3. **Jump optimization**:
   ```rust
   // Before: [Jump(5), ..., /* ip=5 */ Jump(10)]
   // After: [Jump(10), ...]  // ← jump directly to ip=10
   ```

4. **Type propagation**:
   ```rust
   // Core IR: Var("x") type unknown
   // Compiler: locals.get("x") determines I64
   // Bytecode: LoadI64("x")  // ← no type check needed
   ```

#### Performance comparison with a tree-walking interpreter

| Mode | Execution loop | Overhead | Execution speed |
|-----|----------------|----------|----------------|
| **Tree-walking** | `eval_stmt()` → `eval_expr()` → ... | Function calls (stack frames, arg passing) | Slow |
| **Bytecode VM** | `loop { match code[ip] { ... } }` | Array access + enum match | Moderate |
| **JIT** | Native code generation | Compile time | Fast (not allowed on iOS) |

SubsetJuliaVM adopts a Bytecode VM because it is **faster than tree-walking** and **App Store compliant without JIT**.

#### Summary: why convert to Bytecode

```
Direct execution of Core IR (tree-walking):
  ✗ Overhead from recursive calls
  ✗ Implicit control flow, hard to debug
  ✗ Few optimization opportunities

Core IR → Bytecode → VM:
  ✓ Simple loop execution (no function calls)
  ✓ Clear execution position via IP (easy to debug)
  ✓ Explicit jumps (clear control flow)
  ✓ Compile-time optimization opportunities
  ✓ Faster than tree-walking
```

**Conclusion**: Converting Core IR to Bytecode achieves both execution efficiency and debuggability.

## iOS integration

### Swift → Rust bridge

SubsetJuliaVM is implemented in Rust and called from Swift via the C ABI:

```swift
@_silgen_name("compile_and_run_detailed")
func compile_and_run_detailed(
    _ src: UnsafePointer<CChar>,
    _ seed: UInt64
) -> UnsafeMutablePointer<CExecutionResult>?
```

The Rust library is compiled as a **static library** (`.a`) and packaged as an **XCFramework**:
- `aarch64-apple-ios` (device)
- `aarch64-apple-ios-sim` (simulator)

### Error reporting

Errors are returned to Swift with full information:

- **SyntaxError**: invalid Julia syntax (parser level, rare)
- **UnsupportedFeature**: valid syntax but unimplemented (Lowering level)
  - Includes source span (line/column)
  - Includes hint message
- **RuntimeError**: runtime error (VM level)
  - Division by zero, out-of-bounds, undefined variables, etc.

### Deterministic execution

All executions use a **seedable PRNG**. SubsetJuliaVM supports two RNGs:

- **Xoshiro256++** (Julia default RNG)
  - Default algorithm used by Julia's `Random` stdlib
  - Fast with a small memory footprint
  - Seed expansion via SHA2-256 (Julia-compatible)

- **StableRNG** (LehmerRNG, compatible with StableRNGs.jl)
  - For reproducibility
  - Fully compatible with Julia's StableRNGs.jl

Currently, the global RNG is `StableRng`, but migration to `Xoshiro` is being considered to match Julia's default.

- `rand()`, `rand(n)`, `rand(m, n)` produce the same results with the same seed
- Reproducible Monte Carlo simulations are possible
- Same code + same seed = same output

## Implementation highlights

### 1. Fully static pipeline

- **No JIT**: no runtime code generation
- **App Store compliant**: no risk of rejection due to dynamic code generation
- **Predictable**: everything is determined at compile time

### 2. Clear error messages

- **Span info**: pinpoints exact error locations
- **Hint messages**: explain why it fails
- **Three error types**: Syntax, Unsupported, Runtime are clearly separated

### 3. Extensible design

- **Add features by extending the Lowering layer only**
- VM itself does not need to change
- Easy to support new syntax

### 4. Type-safe implementation

- Leverages Rust's type system
- Minimizes runtime errors
- Ensures memory safety

### 5. Pure Julia implementations

- **Complex{T}** and **Rational{T}** implemented in Julia
- **Type promotion rules** (`promote_rule`, `promote_type`) in Julia
- Base library functions (`sum`, `prod`, `gcd`, `lcm`, etc.) in Julia
- Enables Julia-compatible behavior without Rust reimplementation

### 6. Runtime dispatch

- **Multiple dispatch** with type specificity calculation
- **Runtime dispatch instructions** for Any-typed operands
- Supports parametric struct dispatch (`MyStruct{Int64}` matches `MyStruct{T}`)
- **Union type** subtype checking

### 7. Dynamic typing preservation

- **Julia-compliant dynamic typing**: after `x = 1.0; x = 2`, `typeof(x)` returns `Int64`
- Variable types are correctly updated on reassignment
- Avoids incorrect type coercion for mixed-type variables (Int64/Float64)

## Architectural choice: why this design

SubsetJuliaVM's architecture (Parser → Lowering → Bytecode → VM) is a good choice under iOS constraints. Here is a comparison with alternatives.

### Comparison of alternative approaches

| Approach | Implementation cost | Execution speed | iOS support | Extensibility |
|---------|----------------------|----------------|-------------|---------------|
| **① Current: Bytecode VM** | Medium | Medium | ✓ | High |
| ② Tree-walking interpreter | Low | Low | ✓ | High |
| ③ Transpiler (→ Swift) | High | High | ✓ | Low |
| ④ WASM VM | Medium | Medium-High | ✓ | Medium |
| ⑤ JIT compilation | High | Highest | ✗ | Medium |
| ⑥ Register-based VM | Medium-High | Medium-High | ✓ | High |

### ① Current choice: Bytecode stack-based VM

```
Core IR → Bytecode → Stack-based VM
```

**Pros**:
- Relatively simple to implement
- Easy to debug (stack state is clear)
- App Store compliant without JIT

**Cons**:
- Stack operation overhead
- Slower than native execution

### ② Tree-walking interpreter

```
Core IR → Direct execution (recursive evaluation)
```

```rust
fn eval(expr: &Expr, env: &mut Env) -> Value {
    match expr {
        Expr::BinaryOp { op, left, right, .. } => {
            let l = eval(left, env);
            let r = eval(right, env);
            apply_op(op, l, r)
        }
        Expr::Var(name, _) => env.get(name),
        // ...
    }
}
```

**Pros**: simplest to implement, no bytecode compiler

**Cons**: **slowest execution** (function call overhead)

**Assessment**: good for teaching or prototypes, but too slow for practical use

### ③ Transpiler (Julia → Swift code generation)

```
Core IR → Swift source → Swift compiler → native
```

**Pros**: **native speed**

**Cons**:
- **Requires runtime compilation** (cannot run user input dynamically)
- REPL is impossible

**Assessment**: usable as a library, not as an interpreter

### ④ WASM-based execution

```
Core IR → WASM bytecode → WASM runtime
```

**Pros**: same code runs on web and iOS

**Cons**: dependency on a WASM runtime, complex FFI

**Assessment**: used in the web version (subset_julia_vm_web). For iOS, a custom VM is simpler.

### ⑤ JIT compilation

```
Core IR → LLVM IR → native code (runtime generation)
```

**Pros**: **fastest execution** (same approach as Julia itself)

**Cons**: **forbidden by iOS App Store** (dynamic code generation not allowed)

**Assessment**: impossible on iOS. **This is why SubsetJuliaVM exists.**

### ⑥ Register-based VM

```
Core IR → Register-based bytecode → Register-based VM
```

```rust
// Stack-based (current)
PushI64(1)
PushI64(2)
AddI64

// Register machine
LoadImm(R0, 1)
LoadImm(R1, 2)
Add(R2, R0, R1)
```

**Pros**: no stack operation overhead (used in Lua 5.0+, Android Dalvik)

**Cons**: more complex implementation (register allocation)

**Assessment**: **future optimization candidate**. The current stack-based VM is sufficient.

### Why the current choice is appropriate

```
┌─────────────────────────────────────────────────┐
│  SubsetJuliaVM goals                            │
│  • Education and learning                       │
│  • Experiencing Julia syntax                    │
│  • Simple numerical computation                 │
│                                                 │
│  Not required:                                  │
│  • High-performance production workloads        │
│  • Large-scale data processing                  │
│  • Replacing full Julia                         │
└─────────────────────────────────────────────────┘
```

1. **iOS App Store constraints**: JIT is not allowed, so AOT + VM is required.
2. **Implementation complexity**: a stack-based VM is easier to implement and debug.
3. **Extensibility**: new features can be added in the Lowering layer.
4. **Performance**: sufficient for education and demos.

### Future improvement candidates

| Improvement | Effect | Difficulty |
|------------|--------|------------|
| Register machine | 20-30% faster | High |
| Instruction specialization | 10-20% faster | Medium |
| Inlining | Faster loops | Medium |
| Constant folding | Compile-time optimization | Low |

**Conclusion**: The current architecture achieves the right trade-offs for these goals.

## Summary

SubsetJuliaVM is a **fully static pipeline** for running a Julia subset on iOS. It avoids JIT compilation and is designed to pass App Store review.

**Design core**:
- The parser accepts all syntax
- Lowering decides support
- The VM only needs Core IR
- Errors always include spans

This design makes it easy to extend, provides clear error messages, and safely executes Julia code on iOS devices.
